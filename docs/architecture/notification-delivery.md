# Notification Delivery

How a mobile push notification travels from an [instance](../concepts/deployment.md#instances) to a guardian's device, and the invariants that hold across the instance ↔ [Rome Cloud](../concepts/rome-cloud.md) ↔ push-provider boundary. A device receives push through its platform service — APNs for iOS, FCM for Android — and the notification itself originates from a user-directed [action](../concepts/actions.md) or from a [Concierge](concierge.md) turn.

## Components

- **Instance** — runs the agent and the notification action, and the Concierge's turns. Decides *whether* to notify, *whom*, and *what* the body says. Knows which chat each person's phone app shows and whether each person is at a web dashboard, from their signals on the live-events socket.
- **Rome Cloud** — the central push broker. Owns device registration, the push-provider credentials (APNs for iOS, FCM for Android), and the delivery fan-out.
- **Desktop app** — the Rome desktop app. It stays connected to Rome Cloud's device Gateway while it runs signed in, and shows the notifications Rome Cloud sends over that connection.
- **APNs / FCM** — the platform push services (Apple's APNs for iOS, Google's FCM for Android), and the only path to the physical device.

## Invariants

- **An instance never contacts a push provider directly.** All push delivery goes through Rome Cloud. The instance only asks Rome Cloud to notify. The push-provider credentials (APNs and FCM) live solely on Rome Cloud and never on an instance, so a compromised instance cannot push to arbitrary devices.

- **A device's provider is fixed at registration, and dispatch after it is provider-agnostic.** Each device registers under exactly one provider — APNs for iOS, FCM for Android. Rome Cloud resolves the account and the body once, then delivers that same resolved content to each device via its provider. Only the per-device send leg varies by provider. The account-scoping, content-enforcement, no-secrets, and bounded-fire-and-forget invariants hold identically across providers. (Adding a provider also widens the device model and the registration path — the send leg is not its whole footprint.)

- **The instance names only a recipient it serves, and Rome Cloud checks it.** A request carries no user or device identifier. Without `recipient`, Rome Cloud resolves the instance owner's account from the authenticated instance token and sends to that account's registered devices. With `recipient`, a visitor's Rome Cloud account, Rome Cloud sends to that account's devices only if the visitor is on the instance's synced visitor list and has signed in to that instance at least once, in the app or on the web, and answers `recipient_not_allowed` otherwise. Rome Cloud pushes only for a hosted instance. For a desktop, self-hosted or test instance it sends nothing and answers zero counts with `reason: "not_hosted"`, which the instance reports as not delivered, never as sent. The instance remembers that answer for an hour, or until its instance token changes, and asks Rome Cloud nothing meanwhile. An older Rome Cloud sends no `reason`, and its counts stand. A Rome Cloud that does not know the field refuses the request, so a visitor's push never falls back to the owner's devices. The instance treats a success that does not echo the recipient as delivery-ambiguous. [ADR](../adrs/proactive-concierge-push-without-per-message-consent.md#amendment-every-message-pushes-to-the-person-the-chat-serves-unless-their-dashboard-is-active)

- **Rome Cloud also delivers each push to the person's desktop apps, over the device Gateway.** Alongside APNs and FCM, Rome Cloud sends the same title, body, level and chat, plus the instance id, as one `notification` message to the desktop apps of the account the push is for. The desktop app shows it as a system notification unless its Rome window is visible and in front. A click opens the window, and the chat when the app has that instance open. It is a side path of the Gateway, not a relayed message, and runs server to client only. The instance is unchanged: it still only talks to Rome Cloud. A desktop app is connected to the Gateway whenever it runs signed in, whether or not Computer use ("Let Rome use this computer") is on, because Computer use only decides whether Rome may run programs there. The app has its own Notifications switch, on by default. With it off the app still receives the message and drops it, so Rome Cloud still counts the notification as delivered: the Gateway delivered it. Like the phone push, it is fire-and-forget: nothing queues it or retries it, and a message to an app that is not connected is lost. Without a level, the notification is silent. [Gateway protocol](../rome-node.md#rome-desktop)

- **The title is fixed and broker-owned. The body is the only sender-supplied content.** Rome Cloud always sets the notification title and provides the default body. A request may override only the body.

- **A push level and a chat are routing data, never shown.** A request may say whether the push alerts (`active`) or arrives silently (`passive`), and which chat a tap opens. Neither is displayed, so the body stays the only content the guardian reads. Only the instance itself sets them. The agent-facing action supplies a body alone.

- **The notification action fails closed on whom it rings.** In a chat private to one person (a Concierge chat and its task chats), it rings that person. Otherwise it rings the one person the calling turn acts for, whoever owns the chat: a visitor in a chat shared with the guardian or another visitor rings only themselves. In a shared chat with no such person, because no one acted or the turn holds more than one person's input, it sends nothing and tells the agent it cannot tell whom to notify. It never falls back to the chat's owner or the guardian. A call with no dashboard chat rings the guardian. A turn keeps the person whose message started it, from when the message was admitted, and so do its subagents and forks. A turn Rome continues after a restart, a usage limit or an approval acts for the person whose turn it continues, never the guardian who approved, and for no one when that turn held more than one person's input. Every action it calls runs as that person, however late the model's tool call arrives. Another person's input steered or joined into the turn leaves it acting for no one. A routine records the person who created it (the turn's person for one a turn schedules, the signed-in person for one turned on from the dashboard, the guardian for an app's routine), and its fires act for them, so a reminder rings whoever asked for it. A routine from before that record acts for its chat's owner. A visitor's call never reaches the guardian's devices. The agent supplies the body alone, never the recipient.

- **Every message of a Concierge turn with a push level pushes, to the person the chat serves.** A proactive turn and the reply to a message the guardian or a visitor sent, signed in, have a push level. The reminder after a turn, the quota recovery and the "chat retired" notice never push, nor does the reply to a message no person wrote: one said as an agent account or an automated source, or sent by a loopback caller acting as the guardian. A guardian's chat pushes to the guardian, and a visitor's to that visitor, never to the guardian. In one chat, messages within 15 seconds of the last push merge into one push, sent when those 15 seconds end and showing the latest message. A message held back when said never enters the merge, and a newer message always replaces an older one still waiting. A push rings only when the chat's last push is more than 2 minutes old, and a digest never rings. Inside the person's own quiet hours nothing pushes, and the message stays in its chat. The instance knows how a turn started, and never infers it from the text. [ADR](../adrs/proactive-concierge-push-without-per-message-consent.md)

- **Nothing pushes for a chat its person's phone app shows.** The phone app marks its live-events socket with the `x-rome-client: phone` upgrade header and holds the `chat.watch:<chatId>` topic for the one chat on its screen, none under a sheet or its drawer. While that socket holds a chat's watch, the chat counts as watched for the person signed in on it, the guardian or a visitor, and nothing the Concierge says there pushes to that person. The phone's other subscriptions follow chats it does not show and never count. A message skipped this way is dropped, and the chat's next message pushes as usual. A socket holds one watch, outside its subscription cap, and the phone sends it before its other topics. A dashboard's watch never counts: a browser cannot set the header. The phone moves the watch as the chat on screen changes, and drops it and closes the socket as it leaves the foreground, so the count drops at once. A phone killed or cut off without that goodbye counts until the socket's ping drops it, and a message in that window does not push.

- **Nothing pushes to a person while they are at a web dashboard.** While any of a person's dashboards on the instance is active, in any browser, none of that person's Concierge pushes goes out, in any chat, digest included. The guardian's activity holds back only the guardian's pushes, and a visitor's only that visitor's. A dashboard is active for 1 minute after its last `active` signal on the live-events socket. It sends one on keyboard, pointer or touch input while its tab is visible and its window focused, at most once every 30 seconds. It sends `away` as the tab is hidden, the window loses focus or the page closes, and from then it is not active. A socket that closes stops counting at once. The phone's socket never counts. Input inside a same-origin app frame on the dashboard counts as input. A dashboard page inside the phone app's web view never counts as a dashboard and sends no signals: its user agent carries `RomeiOS/`, or, from an app build older than that marker, names an iPhone or iPad without the `Safari/` token every iOS browser carries. A message held back this way is dropped: nothing queues it, and nothing pushes when the dashboard goes idle. The agent-facing action is not affected. [ADR](../adrs/proactive-concierge-push-without-per-message-consent.md#amendment-every-message-pushes-to-the-person-the-chat-serves-unless-their-dashboard-is-active)

- **A Concierge push carries only the Concierge's own words.** Its body is what the Concierge wrote in the message, its text or a forward's intro, or else a fixed line in the dashboard's language. A message the Concierge marks private, a forward with no intro and a card push the fixed line: every message can reach the lock screen, so the Concierge marks one that holds a secret private. Forwarded or quoted text, a task's title and a chat's name never become the body, since any of them may come from a task's output and hold a code or password.

- **A push never holds or fails the turn that caused it.** The message is in the chat before the push is asked for, and a failed or refused push is logged with its outcome only. An instance with no Rome Cloud credential sends nothing.

- **Rome Cloud is the single content-enforcement point.** All validation, normalization, length-capping, and fallback of the body happen at the broker, once, before device lookup and delivery. The instance forwards an agent's body unchanged. A body the instance builds itself, the Concierge's preview line, is shaped for reading before it is sent, and Rome Cloud still enforces every rule on it. The instance never relies on that shaping to meet the broker's rules.

- **Agent input is validated at the instance boundary before dispatch, independently of the broker.** The action fails closed on a malformed argument — a bad request never reaches Rome Cloud and never degrades into a default notification. This is a distinct layer from Rome Cloud's own request validation: the two do not rely on each other.

- **The notification body carries no secrets.** The body may be lock-screen-visible and is retained with the invocation, so it must not contain passwords, authentication codes, tokens, or other secrets. A notification may state that approval is required. It must not carry the secret itself. This is a behavioral rule, not a runtime-enforced filter.

- **Notification content is never written to operational logs.** Neither the instance nor Rome Cloud emits the body to logs. Logs carry only outcome and identifier metadata. (Invocation arguments are retained with the action record under the normal execution-history semantics — a separate concern from logging.)

- **A successful push-provider response (APNs or FCM) is acceptance, not confirmation of delivery or display.** Nothing downstream treats "sent" as "seen."

- **A delivery-ambiguous outcome is never auto-retried.** When a failure surfaces after dispatch — so delivery may already have happened — the result is reported as ambiguous and the caller must not retry without explicit authorization.

- **Delivery is bounded and fire-and-forget.** Each send fans out over the account's registered devices with a bounded per-request cap. There is no queue and no automatic retry.
