# Email and the `Messages` account verbs

Email cannot answer the `Messages` account verbs directly against the mail provider. `readConversation` and `read` are reachable at a price, and `count` is not reachable at all: no layer of the stack — the instance client, the Rome Cloud route, or AgentMail itself — offers a total for a filtered set of messages. AgentMail's list response carries a `count` field that means "Number of items returned" on that page, so the only way to learn how long a history is remains walking it to exhaustion ([`agentmail@0.5.12` `dist/cjs/api/types/Count.d.ts`](https://docs.agentmail.to/api-reference/inboxes/messages/list), "List Messages" response schema). A directory read of P people costs at least two full walks of the mailbox plus P body fetches when the store batches its calls the way the SQL stores do, and 3P walks when it does not. The contract's exhaustion law and its silent-account law both reduce to that walk, so a direct store answers the milestone's question with a mailbox scan per dashboard render. Mirroring email first is the cheaper route, and the inbound push that would feed the mirror already exists.

## What the provider offers

`MailProvider` exposes five operations and no others: `provision`, `send`, `getMessage`, `getAttachment` and `listMessages` (`packages/core/src/lib/rome-cloud-mail.ts:165-173`). `RomeCloudMailProvider` implements all five against `getRomeCloudOrigin()` with the instance token as a bearer credential and a 15-second timeout per call (`packages/core/src/lib/rome-cloud-mail.ts:198-233`). The paths are `/api/instance/mail/provision`, `/api/instance/mail/send`, `/api/instance/mail/message?messageId=…`, `/api/instance/mail/attachment?messageId=…&attachmentId=…` and `/api/instance/mail/list` (`packages/core/src/lib/rome-cloud-mail.ts:268-320`).

`listMessages` accepts exactly five parameters: `after`, `before`, `limit`, `ascending` and `pageToken` (`packages/core/src/lib/rome-cloud-mail.ts:121-132`, sent as query string at `:311-320`). It returns `{ messages, nextPageToken }` and nothing else (`packages/core/src/lib/rome-cloud-mail.ts:134-137`). The paging model is an opaque forward cursor: the caller passes the previous response's `nextPageToken` back and has no way to seek to an offset. There is no filter by sender, by recipient, by thread, or by label, and no count of any kind.

One row of the list carries `providerMessageId`, `threadId`, `from`, `subject`, `preview`, `receivedAt` and `labels` (`packages/core/src/lib/rome-cloud-mail.ts:110-119`). It carries no `to`, no `cc` and no body. `from` is the raw RFC 5322 string rather than a parsed pair. A caller that wants the recipients or the body of a listed message must call `getMessage` for it, which returns the full `RomeMailMessage` including `to`, `cc`, `direction` and the body parts (`packages/core/src/lib/rome-cloud-mail.ts:72-93`).

The Rome Cloud route is reachable from this machine and confirms the client. `GET /api/instance/mail/list` reads `limit`, `after`, `before`, `ascending` and `pageToken` from the query string and passes only those to `listMessagesForInstance` (`amantru/rome-cloud packages/pantheon/src/app/api/instance/mail/list/route.ts:29-45`). It clamps `limit` to a hard ceiling of 100 (`route.ts:17`, `route.ts:32-34`). Authorization is structural: the inbox is resolved from the instance's own identity, never from client input (`amantru/rome-cloud packages/pantheon/src/lib/mail/rome-mail.ts:452-479`). Rome Cloud exposes no thread route and no search route.

The upstream provider offers more than Rome Cloud forwards. AgentMail's list endpoint accepts `labels`, and `from`, `to` and `subject` as repeatable substring filters (`amantru/rome-cloud`'s pinned `agentmail@0.5.12`, `dist/cjs/api/resources/inboxes/resources/messages/client/requests/ListMessagesRequest.d.ts`, confirmed at [docs.agentmail.to, "List Messages"](https://docs.agentmail.to/api-reference/inboxes/messages/list)). Repeated values are AND-ed, so `from` and `to` cannot be OR-ed in one request, and a substring match on an address also matches a longer address that contains it. AgentMail also offers `inboxes.threads.get(inbox_id, thread_id)`, which returns the whole thread with `messages` ordered ascending and a `messageCount` (`agentmail@0.5.21 dist/cjs/api/resources/threads/types/Thread.d.ts`, client at `dist/cjs/api/resources/inboxes/resources/threads/client/Client.d.ts`). Rome Cloud's seam forwards none of this: `listMessages` in Pantheon passes only the same five parameters (`amantru/rome-cloud packages/pantheon/src/lib/mail/agentmail.ts:232-254`) and maps away everything the response carries beyond `messages` and `nextPageToken` (`agentmail.ts:243-254`).

`ThreadMessageCount` is the only count anywhere in the stack, and it counts one thread rather than a person's history (`agentmail@0.5.21 dist/cjs/api/resources/threads/types/ThreadMessageCount.d.ts`). Full-text search exists at `inboxes.messages.search` and `inboxes.threads.search`, ranked by relevance and capped at a limit of 100, which is a different ranking from the one `Messages` pages and cannot serve it.

## How the adapter uses the provider today

`EmailAdapter.fetchHistory` is the one history read, and it powers `fetch_channel_history` rather than any `Messages` verb (`packages/core/src/channels/email.ts:553-627`). It pages `listMessages` newest-first with `after` set to a clock window, applies an optional thread filter per page in JavaScript, and stops at one of three caps (`packages/core/src/channels/email.ts:576-602`). The caps are 200 matched messages, 2000 scanned messages and 50 list calls (`packages/core/src/channels/email.ts:130-143`). The comment on `HISTORY_MAX_SCAN` states the constraint in the adapter's own words: "AgentMail's list has no server-side thread filter, so a thread-scoped fetch narrows client-side" (`packages/core/src/channels/email.ts:133-137`). When a cap bites, the adapter logs `email history truncated` and returns a short answer (`packages/core/src/channels/email.ts:604-616`).

The adapter identifies a person by the normalized email address: lowercased, trimmed, and unwrapped from angle brackets (`packages/core/src/channels/email.ts:86-91`). That address becomes `channelUserId` on both the inbound path and the history path (`packages/core/src/channels/email.ts:487`, `packages/core/src/channels/email.ts:665`). It identifies a conversation by AgentMail's `threadId`, never by the subject (`packages/core/src/channels/email.ts:509`, `packages/core/src/channels/email.ts:670`). Direction is inferred from the `sent` label or from a `from` that matches the instance's own inbox (`packages/core/src/channels/email.ts:661-664`), which is decidable from a list row without a hydration.

Each matched list row is hydrated by a `getMessage` call at concurrency 5, and a hydration miss falls back to the row's preview (`packages/core/src/channels/email.ts:620-622`, `packages/core/src/channels/email.ts:632-643`). So a history of N messages costs N `getMessage` calls on top of the list walk.

## What the contract obliges

`Messages` binds the three account verbs by one law: `count` is the length of the full read, and `latest` is its first entry (`packages/core/src/channels/messages.ts:75-95`). The contract suite asserts both against a real full read (`packages/core/src/channels/messages-contract.ts:64-74`), and asserts that paging with a limit of 2 walks exactly the full read and no more (`packages/core/src/channels/messages-contract.ts:102-122`).

Three obligations a paged mailbox read can satisfy. Ordering newest-first is native, since the provider's default order is descending by timestamp and `ascending` is a parameter (`packages/core/src/lib/rome-cloud-mail.ts:128-129`). A unique cursor position per message is satisfiable, because `providerMessageId` is unique within an inbox and serves as the `ref` the contract requires to be distinct (`packages/core/src/channels/messages-contract.ts:137-143`). An empty page for a conversation the store has never heard of is satisfiable by construction, since an unknown thread id simply matches nothing on the walk (`packages/core/src/channels/messages-contract.ts:226-234`).

Three obligations need N round-trips. A full read of a person's history needs one list walk to find their rows plus one `getMessage` per row to fill `TimelineEntry.body`, because a list row carries only a preview. Paging to exhaustion needs a fresh walk per page, because the contract's cursor is a `TimelineEntry` and the provider's cursor is an opaque `pageToken` that a store cannot reconstruct from an entry. The contract's total order is `at DESC, outbound DESC, source ASC, ref ASC` (`packages/core/src/channels/messages-sql.ts:289`), and the provider orders by timestamp alone, so resuming means re-walking with `before` set to the cursor's timestamp and re-applying the tie-break in JavaScript.

Two obligations cannot be satisfied without a local index. `count` has no primitive at any layer, so its only implementation is a walk of the whole mailbox with the person's rows tallied client-side. `latest` for a silent account is the same walk with an empty tally, and the contract requires both `count` of 0 and `latest` of null for an account the store holds nothing for (`packages/core/src/channels/messages-contract.ts:145-153`). A directory is mostly silent accounts, so the worst case is the common case.

One further obligation the SQL stores meet structurally and a direct store meets only by luck. `activity.ts` raises `count` and `latest` as two separate calls (`packages/core/src/people/activity.ts:62-65`). `sqlMessages` answers a whole batch from a single statement, so the two are read off one ranking of one set of rows and cannot disagree (`packages/core/src/channels/messages-sql.ts:99-117`, `packages/core/src/channels/messages-sql.ts:244-299`). Over HTTP the law holds only if the store walks once and answers both from that walk. A message arriving between two walks makes `latest` an entry the count does not cover.

There is also no truncated answer in the contract. `fetchHistory` is allowed to stop at 2000 scanned messages and say so in a log line. A `count` that stops at 2000 is a wrong count, and the contract has no way to express the difference.

## Direct implementation cost

Let P be the people in a directory read, M the messages in the mailbox within the window, and O the outbound messages among them. The page size is 100, fixed by the Rome Cloud route's ceiling (`amantru/rome-cloud packages/pantheon/src/app/api/instance/mail/list/route.ts:17`). One full walk of the mailbox is therefore `ceil(M/100)` calls to `/api/instance/mail/list`.

A directory render raises three store calls per person. `assignAccountHeads` calls `latest` once per account to decide which store owns it (`packages/core/src/people/timeline.ts:121`). `readPeopleActivity` then raises one `count` and one `latest` per person, all before the first is awaited (`packages/core/src/people/activity.ts:62-65`). That is 3P calls into the `Messages` interface, spread over two microtask ticks.

A direct store that copies the microtask batching in `sqlMessages` (`packages/core/src/channels/messages-sql.ts:369-395`) serves each tick from one walk, because the walk is the same walk for every person on it. The cost is then two walks plus one `getMessage` per person's head to fill its body: `2 × ceil(M/100) + P` HTTP calls. For a mailbox of 10,000 messages and a directory of 200 people, that is 200 list calls and 200 message calls, or 400 round-trips per dashboard render, each on a 15-second timeout (`packages/core/src/lib/rome-cloud-mail.ts:232`).

A direct store without batching pays a walk per call: `3P × ceil(M/100)`, which is 60,000 list calls for the same numbers. Batching is therefore not an optimization here but the difference between a slow page and an unusable one.

Both figures understate the cost, because attributing an outbound message to a person is not decidable from a list row. The row carries `from` and no `to` (`packages/core/src/lib/rome-cloud-mail.ts:110-119`), and on an outbound message `from` is the instance's own inbox. Attributing outbound mail by address alone needs a `getMessage` per outbound row, which adds O calls to every walk — 5,000 calls for a mailbox half of which Rome sent. The escape is to attribute by thread instead: an outbound message belongs to the thread, and the thread's inbound rows name the counterparty. That rule costs nothing extra on the walk and fails only for a thread Rome started that has no reply yet.

Passing AgentMail's `from` and `to` filters through Rome Cloud would not rescue `count`. The filters are AND-ed, so a person's two-directional history needs two requests, and each still has to be paged to exhaustion because the response `count` is a page length. The filters match substrings rather than addresses, so a store cannot trust a filtered result without re-filtering it client-side, which means it cannot trust a filtered page count either. The one verb the filters would genuinely cheapen is `latest`, from a full walk to two requests of limit 1 per person, or 2P calls for a directory.

`readConversation` is the one verb with a clean remote answer available upstream. `inboxes.threads.get` returns the thread's messages in one call with a `messageCount` beside them. Rome Cloud exposes no route for it, so today the verb costs the same mailbox walk that `fetchHistory` already pays, filtered by `threadId` in JavaScript and truncated at 2000 scanned messages (`packages/core/src/channels/email.ts:583-602`). Adding one Rome Cloud route would turn a bounded-but-truncating walk into a single exact call.

Compare the SQL stores. `whatsAppMessages` and `linkedInMessages` take nothing but the database (`packages/core/src/channels/whatsapp-messages.ts:32`, `packages/core/src/channels/linkedin-messages.ts:26`), and every one of their four verbs becomes a job on a queue that a single statement answers for the whole batch (`packages/core/src/channels/messages-sql.ts:118-149`). `count` is a window function read off the same ranking as the page, with an explicit frame so it reports the length of the history rather than a running total (`packages/core/src/channels/messages-sql.ts:273-292`). A directory of a thousand people costs one query. `agentMessages` answers the same way over `rome_agent_messages` joined to `rome_sessions`, keyed by the `(channel, thread)` pair (`packages/core/src/channels/messages-agent.ts:60-97`). The gap is one query against 400 HTTP round-trips, and a count that is exact against one that is capped.

## Mirror option

No email persistence exists. `packages/core/src/db/schema/system.ts` holds `wa_contacts`, `wa_chats`, `wa_messages`, `linkedin_threads`, `linkedin_messages`, `linkedin_participants` and `sentinel_log`, and no table for mail. A grep for `email_messages`, `mail_messages` or an equivalent cache across `packages/core/src` returns nothing. The only email column anywhere is `guardian_auth.email` and `provider_accounts.email` (`packages/core/src/db/schema/system.ts:361`, `packages/core/src/db/schema/system.ts:374`), neither of which holds a message.

Two channel-agnostic stores do already hold part of email's history. `agentMessages` reads `rome_agent_messages` keyed by `(source_channel, source_thread_id)` (`packages/core/src/channels/messages-agent.ts:66`), and `sentinelLogMessages` reads `sentinel_log` keyed by `(channel, channel_user_id)` for the account scope and `(channel, thread_id)` for the conversation scope (`packages/core/src/channels/messages-sentinel.ts:26-30`). Every inbound email that reaches `messageHandler` lands in one of the two under `channel: "email"` with the normalized address and the AgentMail thread id (`packages/core/src/channels/email.ts:521-535`). Both are in `personMessageStores` already (`packages/core/src/people/timeline-sources.ts:47`). So a person who has written to Rome by email already has a readable history, and what is missing is the mailbox's own record: mail that arrived while the instance was down, mail sent outside a turn, and anything older than the instance.

A mirror has one advantage over the WhatsApp and LinkedIn syncs. The inbound push already exists and is already verified: `ingestInbound` receives every message from the Rome Cloud relay with an HMAC check (`packages/core/src/channels/email.ts:431`, `packages/core/src/channels/email.ts:680-687`). A mirror writer hangs off that one call. Outbound is `sendMessage`, whose provider result carries both `messageId` and `threadId` (`packages/core/src/channels/email.ts:352`, `packages/core/src/channels/email.ts:367`, `packages/core/src/lib/rome-cloud-mail.ts:286-297`). Backfill is one `listMessages` walk at provision time, paged with the cursor the client already exposes.

The mirror's rows map onto the `MessageViewSql` columns without a gap. `source` is the constant `"email"`, `key` is the normalized address for an account read and the thread id for a conversation read, `at` is `receivedAt`, `outbound` is the direction the adapter already infers, `ref` is `providerMessageId`, and `body` is the Markdown the adapter already produces (`packages/core/src/channels/messages-sql.ts:23-41`, `packages/core/src/channels/email.ts:630-678`). An email store would then be `sqlMessages` over that view, built at boot from the database alone, exactly like the two stores in `channel-list.ts:34-37`.

A store is necessary but not sufficient for the People surface. Email has no `Accounts` implementation, so nothing folds a person's addresses onto an email account and email is absent from `channelList` entirely (`packages/core/src/channels/channel-list.ts:34-37`). A channel entry may carry a null address book (`packages/core/src/channels/channel.ts:56-68`), and an email entry would need one only if a person can hold several addresses that must read as one history.

## Open items

1. Decide whether Rome Cloud gains a thread route. `inboxes.threads.get` answers `readConversation` in one exact call, and its absence is the reason the conversation read costs a truncating mailbox walk today.
2. Decide whether Rome Cloud forwards AgentMail's `from`, `to` and `labels` filters. The filters cheapen `latest` and do nothing for `count`, so the decision only matters under a direct implementation.
3. Settle the outbound attribution rule for a mirror as well as for a direct store. Attributing by thread costs nothing and fails for an unanswered thread Rome started, and attributing by address costs one `getMessage` per outbound message.
4. Decide whether email needs an `Accounts` implementation, which turns on whether one person holds several mail addresses that must read as one history.
5. Confirm AgentMail's rate limits against the walk figures above. This report reads the SDK types and the public endpoint reference, and neither states a per-inbox request budget.
