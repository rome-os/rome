# How this environment differs from production

Each difference below is deliberate. A rule that passes here can still fail in production for the reason a difference names, so the final check for R1 to R7 is a live run in a real Slack test workspace.

| Area | Production | This environment | What it can hide |
|---|---|---|---|
| Slack | slack.com: the real approve screen, Web API and event delivery | The fake Slack in `fake-slack/`. It implements only `oauth.v2.access`, `auth.test`, `auth.revoke`, `chat.postMessage`, `conversations.open`, `conversations.list`, `users.conversations`, `conversations.info`, `conversations.history`, `conversations.replies`, `users.info`, `users.list`, `bots.info`, `reactions.add` and `search.messages`, and the events `message.im`, `app_mention`, `app_uninstalled` and `tokens_revoked`. Its payloads follow Slack's documented shapes, not captured traffic. It checks bot and user token scopes for those methods and events only, and takes the bot's group membership from the workspaces file (`bot_member: false` leaves it out) with no way to join or leave, so `conversations.join` and invites are not modelled. Outside a group, a bot token gets `not_in_channel` on reads, reactions and posts, and posts only with `chat:write.public` in a public group. A user token reads, reacts and posts only in its own member's direct message and in the private groups its member is in, and gets `channel_not_found` elsewhere; public groups are open to it. `search.messages` matches every word of the query as a substring of a message's text, without Slack's query syntax (`in:`, `from:`, quotes) or ranking. It has no redirect URL allow-list. | A field Slack sends that the fake leaves out, a scope a method the fake lacks would need, `not_in_channel`, a real redirect URL mismatch. |
| Thread reads | `conversations.replies` answers the messages between `oldest` and `latest`. Its docs do not say whether the parent comes back when the window leaves it out. | The window bounds every message, the parent too. | Code that counts on the parent always being in the answer passes in Slack only if Slack does include it. |
| Rate limits | Slack's tiers for every method, and for an app outside the Marketplace installed after 29 May 2025, `conversations.history` and `conversations.replies` at 1 request a minute and 15 messages a request | Only that limit on those two methods, per method and workspace, on unless switched off; every other method is unlimited. The 429 carries `Retry-After` in whole seconds. | A tier limit on another method, such as `chat.postMessage` at about one message a second per conversation. |
| Reinstall | Slack issues a new bot token. Its docs do not say whether the bot user id changes; reports from people who tried it say it stays. | A new bot token, the same bot user and bot id. | A bot user id that changes on reinstall, which would break matching the connection to its account. |
| Removal order | Slack's docs say `tokens_revoked` is sent once tokens "are revoked" and that an app "is not uninstalled until its final user and bot tokens are revoked", and that the two events may come in either order. They do not state the token's answer at the moment of delivery. | The fake revokes the tokens, then sends `tokens_revoked` and then `app_uninstalled`, always in that order. | Code that depends on the order of the two events, or a Slack that delivers an event before its revocation has reached every API host. |
| Distribution (R2) | Slack's docs name `invalid_team_for_non_distributed_app` ("attempting to install/authorize an undistributed Slack API app on a team where the app was not created") but do not say where it appears: on the approve screen, on the redirect, or from `oauth.v2.access`. | The approve screen answers 403 with the code on the page and redirects nowhere, so the app's callback is never reached. | A Slack that redirects to the callback with `error=invalid_team_for_non_distributed_app`, which the product would then show its own way. |
| Older apps (R10) | Each app is its own bot user with its own direct messages, created on api.slack.com by the guardian or by Rome Cloud. Socket Mode reconnects on Slack's schedule (`disconnect` frames, a refresh about every few hours). | `POST control/other-app` installs one with its tokens. Its bot user is its own (`UOTHER…`), but a direct message with a member keeps the same conversation id for every app, and posts record which app made them (`appId`). The fake never sends `disconnect` frames, and events reach a Socket Mode app only through `control/socket-event`. | Code that tells apps apart by the direct message's id, or a reconnect path that only a `disconnect` frame triggers. |
| Old scopes (R14) | A workspace that approved Rome's app when it asked for fewer scopes keeps that install's scopes until a member approves the app again; Slack does not add new scopes by itself. | `POST /_control/grant-limit` caps what a sign-in from that workspace grants, so a fresh sign-in leaves an install with only the old scopes. Lifting the cap and signing in again stands in for approving the app again. | An approval of only some new scopes, which Slack's screen does not offer; a scope change Slack applies without a sign-in. |
| Upgraded instance (R10) | An instance that ran main has the two older Slack connections because the guardian connected them: `slack_bot` by pasting a Socket Mode app's bot and app-level tokens into its setup, `slack` through Rome Cloud's earlier OAuth app. The upgrade restarts it on the new commit with its data kept. | `ctl.sh old-connections <instance>` (or `up.sh --old-connections`) stops the instance, then in its image installs both apps in the fake and writes the rows into its `rome.db` and starts it again on the commit under test; the instance never ran main. It writes what main writes, read from main's code (`slack-bot.ts`, `oauth-providers.ts`, `providers-import.ts`, `registry.ts`, `repository-db.ts`, `channel-records.ts`, `connected-accounts.ts` and `index.ts` are the same on main and on the product branch): for each kind a `connections` row (a random id, the kind's name as label) and an authorized `connection_grants` row (credential `{material: {kind: inline, record}, expiresAt: never}`, platform `slack`, a random grant epoch). The bot's profile is setup's (auth.test, then bots.info for the app) and its account `team/bot user`; the OAuth profile is Rome Cloud's (`team:installer`, the installer from users.info, the old app's scopes) and its account the subject. The bot also gets the rows main's `connected` event writes: a channel with an opaque id, its connected account with no agent, and its name in `account_profiles`. It links no agent: the bot's kind decides it, and the command reads it from `GET /api/connections`. `old-connections.test.mjs` checks each profile against its kind's strict schema in rome's source; the command checks that rome lists both connections, that the bot's Socket Mode connection is open after the restart, that rome reports an agent for the bot, and that the OAuth tokens reached the connector's token file. | A row main writes that the command misses, such as one from a boot pass of an older main or a migration that rewrote rows on the way; a different connect time for each kind; an agent a guardian linked on main, which the kind's agent now replaces. |
| Slack's address | Slack's base URL is `https://slack.com` | Rome Cloud gets `SLACK_APP_BASE_URL` and the instances get `SLACK_API_BASE_URL`, both `http://127.0.0.1:47200`. Inside the network the fake also answers as `https://slack.com`, with the environment's own certificate trusted through `NODE_EXTRA_CA_CERTS`, so code that ignores the setting still reaches the fake. | Code that reads the setting in one place and hardcodes `slack.com` in another passes here. |
| Event retries | Slack retries a delivery that gets no 2xx after about 0 s, 1 min and 5 min | After 1 s, 10 s and 30 s | Nothing for correctness; dedupe by event id is exercised sooner. |
| Event signing | Slack's signing secret for the official app | A secret generated on each fresh start, shared by the fake and Rome Cloud only | Nothing: same scheme (`v0=` HMAC SHA256 over `v0:{timestamp}:{body}`). |
| Workspaces | Real workspaces, with the app reviewed and distributed | Two fake workspaces, A (Acme) and B (Bayside), with three members and one group each (`config/workspaces.json`) | Enterprise Grid, shared groups, and workspaces with many members. |
| Rome Cloud | Deployed Pantheon (`next start`, production mode) on its own host with Caddy and the reconciler | Pantheon from the given rome-cloud commit, run with `next dev` (development mode), its own Postgres, no Caddy, no reconciler | Production-only code paths. The dev sign-in (`PANTHEON_DEV_IDP`) only works in development mode, which is why it is used. |
| Guardian sign-in to Rome Cloud | Google, Microsoft or password | Rome Cloud's dev sign-in, for two accounts the environment creates: `guardian-a@slackenv.test` and `guardian-b@slackenv.test` | Nothing about the Slack app; it follows the same authorize, consent and token steps afterwards. |
| Instance enrollment | The guardian clicks through the consent page, or the instance is provisioned with a token | `tools/enroll.mjs` does the guardian's clicks over HTTP: the instance's Rome Cloud sign-in, the consent form, the callback | A consent page change that needs JavaScript would break enrollment here first. |
| Webhook relay | Cloudflare Workers and Durable Objects at `ingest.romeos.io` | The same relay code from the given rome-cloud commit, run unmodified by `wrangler dev` (local workerd), with a key pair generated per fresh start | Cloudflare edge limits and colo behavior. |
| Instances | One VM per instance, provisioned by Rome Cloud, behind Caddy with its own domain and HTTPS | Two containers from the given rome commit's production `Dockerfile`, each with its signer, on `http://127.0.0.1:47181` and `:47182`. Chrome and the WeChat client are off. | HTTPS-only cookie behavior and anything that needs Chrome. |
| The agent's model | Whatever the Concierge picks (Opus 5.5 when Claude is connected) | Every model request goes through `tools/model-proxy.mjs`, which pins it to Haiku 5.5 and adds the credential. Rome still believes it picked its usual model. | Answers that only a stronger model gets right; R4 and R6 count replies, not their quality. |
| The model credential | The guardian's own Claude login or Rome credits | One credential from the host running the environment, held only by the model proxy | Login and credits behavior. |
| Wiping Rome's copy (R13) | No such operation; a chat's copy is only lost by accident | `ctl.sh wipe-chat` deletes the rows and transcripts with the instance stopped (README) | A copy kept where the words are transformed (hashed, summarised) survives the sweep, which matches text only. |
| Mail | Rome Cloud provisions Rome's email inbox through AgentMail | No mail provider: an instance's mail provision gets 500 ("AGENTMAIL_API_KEY is not set") at start, a known warning unrelated to Slack | Anything about email. |
| R6 outage | The instance is offline for up to 1 hour | The instance is stopped for 2 minutes (`ctl.sh stop`, then `ctl.sh start`) | Mailbox expiry or drain-key expiry over a longer outage. |
