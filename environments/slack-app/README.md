# Slack app test environment

Everything the official Slack app and its verifier need to run with no person present: a fake Slack, Rome Cloud and the webhook relay, and two Rome instances enrolled in that Rome Cloud. The rules it serves are in the project's rule set (R1, R3, R4, R6, R7, R11 in phase 1). How it differs from production is in [DIFFERENCES.md](DIFFERENCES.md).

## Start and stop

```bash
environments/slack-app/up.sh --rome <ref> --rome-cloud <ref>   # default origin/main for both
environments/slack-app/ctl.sh stop rome-a                       # and start, status; logs <service>
environments/slack-app/ctl.sh wipe-chat rome-a DA000A0000BOB01      # wipe Rome's copy of one chat
echo 'select count(*) from users' | environments/slack-app/ctl.sh cloud-query
environments/slack-app/down.sh                                  # removes containers, volumes and .state
```

`up.sh` needs Docker with Compose, Node 22 or later and git. It finds the rome-cloud checkout at `$ROME_CLOUD_DIR`, else next to this rome checkout. It needs one model credential, `SLACKENV_ANTHROPIC_API_KEY` or `SLACKENV_CLAUDE_OAUTH_TOKEN` (or the files `~/.config/slackenv/anthropic-api-key`, `~/.config/slackenv/claude-oauth-token`), which only the model proxy holds. `--cloud-only` starts everything but the instances and needs no credential.

It runs only committed code. It refuses to start when this folder has uncommitted changes, and it checks rome and rome-cloud out at the given commits into fresh worktrees under `.state/`, so nothing uncommitted in either checkout reaches the environment. The first start of a rome commit builds its production image, which takes several minutes.

When it is ready it writes `.state/env.json` (gitignored): the scratch checkouts of rome (with its dependencies installed, so `pnpm lint:imports` runs there) and rome-cloud, the rome-cloud base ref to diff against, the commits of the environment, rome and rome-cloud, the agent model and effort with the model proxy's counts (`agent.model_proxy`), the fake Slack's address and control API (with `batch`, `posts`, and each workspace's `full_members` and `groups_with_bot`), Rome Cloud's address, Rome Cloud's read-only query command, and each instance's address, guardian, signed-in guardian session, and its controls (stop, start, status, wipe_chat, logs). `copy` names the copy's compose project, port base and state folder.

## Two copies side by side

One variable names a copy and one moves its host ports, so a second copy runs beside the first on one machine:

```bash
environments/slack-app/up.sh --project ambient --port-base 47300   # or SLACKENV_PROJECT=ambient SLACKENV_PORT_BASE=47300
environments/slack-app/ctl.sh --project ambient stop rome-a          # every ctl.sh command takes --project first
environments/slack-app/down.sh --project ambient                    # this copy only; --images removes its own images
```

- The name (`--project` or `SLACKENV_PROJECT`, default `slackenv`) is the compose project, so the containers, volumes and network are the copy's own. The default copy keeps `.state` and the image names `slackenv-rome:<sha>` and `slackenv-rome-test:<sha>`. Any other name gets `.state-<name>` and the images `slackenv-<name>-rome:<sha>` and `slackenv-<name>-rome-test:<sha>`. `live` and `slackenv-live` are refused, as they are `live.sh`'s.
- The port base (`--port-base` or `SLACKENV_PORT_BASE`, default `47100`) sets every host port as an offset from it: Rome Cloud `+0` (and its plain port `+1` with the Worker), the instances `+81` and `+82`, the browser `+90`, the model proxy's control port `+91`, the Worker `+92` and the fake Slack `+100`. With the default base these are the addresses in the table below. Before it starts anything, `up.sh` refuses a port that a container of another compose project publishes, or serves with `--port` on the host's network (another copy's browser).
- The forwarders allow two copies. Each instance, Rome Cloud and the Worker run in the network namespace of their own forwarder, which maps the copy's own port numbers, so `http://127.0.0.1:<base>` is that copy's Rome Cloud on the host, in its browser and in each of its containers. The fixed ports inside the containers (3100, 8080, 8788, 9368) are in each container's own namespace and never meet the other copy's. The network aliases (`slack.com`, `slack.romeos.io`, `relay.slackenv.test`) are on each project's own network. The browser shares the host's network and serves on the copy's `+90` port; its hosts entry for `slack.romeos.io` is in that container only.
- `ctl.sh` and `down.sh` act on one copy only: its state folder, the environment values in it and its project label. A named copy's env.json is in its state folder, and its commands carry `--project <name>`. The default copy's env.json is as before.

## Controls

- `ctl.sh connect <instance>` connects Rome's Slack app to the instance as its guardian, in the guardian's own workspace (Acme for rome-a, Bayside for rome-b), the way the dashboard's Connect and a browser do: it starts the `slack_app` bot setup, signs the guardian in to Rome Cloud with the dev sign-in, follows the sign-in to the fake Slack's approve screen (`https://slack.com` is the fake's port from the host), presses Allow, and waits for the setup to end (`tools/connect-slack.mjs`). An instance that already holds a `slack_app` connection is left as it is. It prints `{instance, outcome, connection_id, path}`, with outcome `connected` or `already`, and exits 0 once the instance is connected; `refused` or `stuck` exit 1 with a `reason`. Rome keeps the connection across `stop` and `start`.

- `ctl.sh wipe-chat <instance> <conversation id>` wipes Rome's copy of one Slack conversation, which the product offers no way to do. It stops the instance, runs `tools/wipe-chat.mjs` on its database in the instance's image, and starts the instance again if it was running. Gone afterwards: the Slack app connection's own copy (`slack_app_messages`) on a Rome that still keeps one (a table that is not there is skipped), the chat's messages (`chat_messages`), the chat's conversations with Rome's agents (`rome_sessions` of the chat and their sub-sessions, with their messages, traces, outputs and per-message rows), and the agent provider sessions of those conversations with their transcripts on disk, so the next message starts a model thread that knows nothing of the old. The chat's place and address stay, and so do the connection and memory. Then, in every other table, it deletes each row whose text holds the conversation id or a wiped message's text (plain or JSON-escaped), so copies in approvals, action runs and later Slack app connection tables such as `slack_app_timeline` go too. A conversation the sweep took a message from, such as a dashboard chat that quoted the words, also loses its agent provider sessions and their transcripts, and they are listed in `provider_sessions`. Last, it searches every text column again and prints JSON with what it deleted (`deleted`), what still holds content (`remaining`), and the places that name the conversation but hold no message (`kept`, which can list only the `chats` and `chat_addresses` tables; the top-level `chats` is the list of wiped chat ids). A place or address that holds a wiped text, such as a chat's title, has that column cleared and listed under `scrubbed`; if it cannot be cleared it counts under `remaining`. `deleted` counts rows per table. `remaining` and `kept` count, per table and column, the rows whose column holds the conversation id or a wiped text, so a row that holds them in two columns is counted under each. It exits 0 when `remaining` is empty, 3 when it is not. `ctl.sh wipe-chat <instance> <conversation id> --text <text> [--text <text>]...` also removes what Rome distilled from the chat, such as a fact the Concierge saved to memory: every row in any table that holds one of the texts (plain or JSON-escaped), and in every text file under the instance's homes (the memory folder included) each line that holds one, a file left empty going too. A transcript (`.jsonl`) that holds one goes whole, with its provider session. Each text must be 8 characters or more, so it cannot match an id or a hash. Those lines are counted under `deleted["(files)"]`, and a file still holding a text is listed under `remaining["(files)"]` by path. Without `--text`, the wipe is as above. History in a git repository (a profile's `.git`) is not rewritten or searched.
- `ctl.sh token-file <instance>` prints whether the instance holds `/run/rome/slack-oauth-token`, the file the connector app reads its Slack tokens from, and the last 6 characters of the bot and user tokens in it.
- `ctl.sh port <instance> <op> '<json>'` makes one call to the Slack app connection's own port, the one the connector app uses, and prints JSON. It is a test-only path through surfaces the product already has, and each call costs one dashboard turn: `tools/port.mjs` opens a dashboard chat as the guardian and sends a marked message, and the environment's model proxy answers that turn itself (`tools/port-script.mjs`) with exactly one `execute_action` call to `connector:connector_proxy`, then ends it; the chat is deleted afterwards. Rome asks for the new chat's title beside the turn; that request has its own system prompt and a structured answer, gets a short text, and never takes the call. A timeout lists each model request the job saw and what it was given. No model reads or judges anything, and the call is never retried or rewritten. Ops: `send {chat, text, thread?}` (`chat.postMessage`), `read {chat, ...}` (`conversations.history`), `thread {chat, ts, ...}` (`conversations.replies`), `groups {...}` (`conversations.list`) and `call {method, args}` (any method, as given); extra fields go to the method as they are. It prints the action's result as Rome returned it. A refusal prints `{"refused": "<why>", "at": "connector" | "rome"}` and exits 0: `connector` when the action ran and answered with an error (Rome's `GET /api/action-executions` shows it ran), `rome` when Rome stopped the call before the action answered (an unknown action, an approval, a thrown error). A turn that made no call prints `{"error": …}` and exits 1. The marker means something only to the isolated environment's model proxy, which takes jobs on its control port (`127.0.0.1:47191`) and refuses a marker naming no job rather than pass it to a real model; the live stack's model proxy has no control port and forwards everything as before.
- `ctl.sh old-rows <instance>` says, read-only and with the instance running or stopped, whether the rows `old-connections` wrote are still in the database: `{"slack_bot":{"connection_id":"…","stored":true},"slack":{…}}`, `stored` true only when both the `connections` row and its `connection_grants` row are there (`tools/old-rows.mjs`). It prints nothing the rows hold. It takes the ids from `.state/<instance>-old-connections.json`, and without that file prints an error and exits 1.
- `ctl.sh gateway-probe rome-a|rome-b` checks the slack-gateway Worker as that instance, with its signer, in its guardian's workspace: health, a 403 for a method the connection does not make (with no call at the fake Slack), connect with the instance's own mailbox, bind through `/internal/bind`, a signed event answered 200, and that event in the mailbox with `x-rome-slack` and a signature the deposit key verifies. It drains the mailbox, so stop the instance first. One JSON object; exit 0 when every check passed.
- `ctl.sh as-instance rome-a|rome-b <file.mjs> [args]` runs a Node file as that instance: in its network, with its signer socket at `SLACKENV_SIGNER_SOCKET`, Rome Cloud's origin in `SLACKENV_CLOUD`, the Worker in `SLACKENV_GATEWAY` and the fake Slack in `SLACKENV_SLACK`, in a one-off container of its image, so it works with Rome stopped. Test only.
- `ctl.sh mailbox rome-a|rome-b` prints the instance's relay mailbox as Rome Cloud hands it out, `{depositUrl}`.
- `ctl.sh find-secret rome-a|rome-b '["<string>", ...]'` counts, read only, where the instance stores any of the strings: `db:<table>.<column>`, `grant:<connection id>`, `file:<path>` under the homes and /run, and `logs`. It prints `{places: {place: [count per string]}, total}` in the strings' order, and never the strings or what holds them.
- `ctl.sh logs <service> [--since <RFC 3339 time>] [--tail <lines>|all]` prints a service's log: the last 500 lines by default, everything since a time with `--since`, both limits when both are given.
- `ctl.sh record <instance> '{"chat":"<conversation id>[:<thread ts>]"}'` prints the messages Chats has on record for a Slack conversation, as `{chat, db, chats, messages: [{key, text, at, thread?}]}` in the order they were said. With a thread ts it lists the thread's first message and its replies. It finds the chat as `wipe-chat` does (by key, by the member's direct message key, or by address) and opens the database read-only (`tools/chat-record.mjs`), inside the running instance or, when it is stopped, in its image.
- `ctl.sh old-connections <instance>` gives the instance the two older Slack connections an upgrade from main leaves, for R10: a guardian's own Socket Mode bot (`slack_bot`) and Rome Cloud's earlier OAuth app (`slack`), both in the guardian's workspace (Acme for rome-a, Bayside for rome-b). It stops the instance, and in the instance's image installs both apps in the fake Slack and writes the rows main writes into its database, so the tokens never leave that process (`tools/old-connections.mjs`; DIFFERENCES.md lists them), and starts it again. Nobody links an agent: the bot's kind decides it. It prints each connection's `connection_id`, `account_id`, `app_id` and `bot_user_id` with its checks, the bot's agent as `GET /api/connections` reports it among them (`checks.bot_agent`), saves them to `.state/<instance>-old-connections.json` (no tokens), and exits 0 once the rows are written and the instance is healthy again. The checks report what the instance made of the rows and judge nothing: a Rome that still knows the two kinds lists both, reports the bot's agent, opens its Socket Mode connection and writes the token file, and one that no longer does ignores the rows. The rows need only the core tables (`connections`, `connection_grants`, `channels`, `connected_accounts`, `account_profiles`), so the command works on a Rome whose code has dropped either kind. Run again, it keeps the connections it wrote. `up.sh --old-connections <instance>` runs it before env.json is written, which then lists them under the instance.
- `ctl.sh product-tests <file>...` runs test files of the rome commit under test, unchanged, for R9's existing tests. Paths are repo-relative. The first call for a commit builds `slackenv-rome-test:<commit>` from a `git archive` of `.state/rome-src` with `test-runner/Dockerfile` (a full `pnpm install --frozen-lockfile`, several minutes); later calls reuse it. Each file runs, with no network, in the package whose rstest config takes it (`rome_apps/*` under `packages/core`), as `scripts/test-env.sh rstest run`. It prints rstest's output, then a last line `{ok, commit, runs: [{package, files, exit_code}], error?}`, and exits 0 when every run passes, 2 when a file is not in the commit, 126 when the test image lacks a file (the runner cannot check it), otherwise the first failing run's code. The image keeps the test files: `test-runner/Dockerfile.dockerignore` takes the place of rome's own `.dockerignore`, which leaves them out of the instance image. `ctl.sh product-tests --add <host file>=<repo-relative path>` (repeatable, among the files) runs a file the commit does not have, such as a verifier's own test, the same way: it is mounted read-only at that path in each run and runs in the package whose rstest config is nearest it, so the path must be one that config's `include` takes. A path the commit already has is refused with exit 2, so no product file is replaced. The commit's own files can be listed beside it, or left out.
- `browser` (a compose service) is Playwright's image at the version rome pins, serving `playwright run-server` on the host's network at `127.0.0.1:47190`, so the verifier drives a browser without installing one. `up.sh` installs the matching `playwright-core` client into `.state/browser-client`. env.json `browser` names the endpoint and the client: `(await import(browser.import)).chromium.connect(browser.ws_endpoint)`. `down.sh --images` also removes the test images.
- `ctl.sh distribution on|off` turns the app's public distribution on or off in the fake Slack.
- `ctl.sh usage [--since <time>] [--until <time>]` prints what the model proxy counted for the message turns that ended in that span (RFC 3339 or epoch milliseconds; either end may be left open): per model sent, the turns, how many at each effort, how many failed, the input, output, cache-write (5 minutes and 1 hour apart) and cache-read tokens the upstream reported, and the cost at list prices, with the total in `cost_usd` and the prices used. The proxy counts in memory, from its own start (`counted_since`). env.json names it as `agent.model_proxy.usage_command`, and the same answer is at `agent.model_proxy.usage` (`GET /_usage?since&until` on the proxy's control port); `agent.model_proxy.stats` counts requests by the model Rome asked for (`asked`) and by model and effort sent (`sent`).
- `ctl.sh cloud-query` reads one SELECT (or WITH) query on stdin and prints its rows as a JSON array. It runs as `slackenv_reader`, a role that can only read, inside a read-only transaction.

## Fake Slack

`fake-slack/server.mjs` stands in for `slack.com`. It has no dependencies and runs on Node 22 or later. Its tests, and those of the tools, run with `node --test environments/slack-app/fake-slack/*.test.mjs environments/slack-app/tools/*.test.mjs`. The wipe's test builds a database from Rome's migrations; `ROME_SRC=<rome checkout>` picks whose (by default this checkout's).

It serves:

- the approve screen, `GET /oauth/v2/authorize`, with the usual `client_id`, `scope`, `user_scope`, `redirect_uri` and `state`. Pressing Allow redirects to `redirect_uri` with `code` and `state`. Pressing Cancel redirects with `error=access_denied`. Optional `team` and `user` query parameters pick the workspace and the member signing in, and so does `POST /_control/sign-in`.
- Socket Mode for another app's app-level token: `apps.connections.open` answers `wss://wss-primary.slack.com/link/?ticket=…`, which the fake serves (that name is in its certificate and the network), saying `hello` and taking an ack per envelope. An app-level token can call nothing else, and a bot token cannot open it (`not_allowed_token_type`).
- the Web API under `/api/{method}`: `apps.connections.open`, `oauth.v2.access`, `auth.test`, `auth.revoke`, `chat.postMessage`, `conversations.open`, `conversations.list`, `conversations.info`, `conversations.history`, `conversations.replies`, `users.info`, `users.list`, `reactions.add` and `search.messages`. Arguments come as a form, JSON or a query, and the token as `Authorization: Bearer` or `token`. Unknown methods answer `unknown_method`. Every answer to a known token carries its scopes in `x-oauth-scopes`, and `oauth.v2.access` names in `scope` every scope the bot token holds, not only the ones asked for, as Slack does. Every call is recorded, a refused one with its error.
- scopes, as Slack checks them: a bot token holds the scopes the install's sign-ins asked for, a user token the user scopes of its own sign-in, and a method the token lacks the scope for answers `missing_scope` with `needed` and `provided` (`chat.postMessage` needs `chat:write`, `conversations.open` `im:write`, `users.info` and `users.list` `users:read`, `reactions.add` `reactions:write`, `search.messages` `search:read`, `conversations.list` and `conversations.info` `channels:read`, `groups:read`, `im:read` or `mpim:read` for each kind of conversation asked for, and a history read `im:history`, `channels:history` or `groups:history` by the kind of conversation). `search.*` answers a bot token `not_allowed_token_type`. Each recorded call carries its `tokenKind`, the `scopes` the token held, and `needed` when it was refused for one. Slack sends no event the install lacks the scope for: `message.im` needs `im:history` and `app_mention` `app_mentions:read`, and the control call that would send it answers 409. `users.info` leaves a member's `profile.email` out unless the install holds `users:read.email`.
- the app's own posts in a direct message, sent back to it as a signed `message.im` event with its `bot_id` and bot user, right after `chat.postMessage` answers, as Slack does. An app must ignore them. `POST /_control/config {self_events: false}` stops them.
- what was said. Every direct message, mention, group message and post is kept in its conversation, with threads: a reply carries `thread_ts`, and its parent `reply_count`, `reply_users` and `latest_reply`. `conversations.history` answers a conversation's top-level messages newest first, and `conversations.replies` a thread oldest first with the parent at the top. Both take `limit`, `cursor`, `oldest`, `latest` and `inclusive`, and answer `has_more` and `response_metadata.next_cursor`.
- Slack's limit for an app outside the Marketplace on those two methods, on by default: one request a minute per method and workspace, at most 15 messages a request (also the default), and HTTP 429 `ratelimited` with `Retry-After` beyond that. `POST /_control/config {history_limit: false}` lifts it to Slack's ordinary page size (default 100, at most 999) with no rate limit.
- events, posted to the configured events address and signed as Slack signs them: `X-Slack-Request-Timestamp` and `X-Slack-Signature: v0=` HMAC SHA256 of `v0:{timestamp}:{body}` with the signing secret. An event that gets no 2xx is retried with `X-Slack-Retry-Num` and `X-Slack-Retry-Reason`.

The workspaces and their members are in `config/workspaces.json`: workspace A `TA0000AAAA` (Acme) and workspace B `TB0000BBBB` (Bayside), each with a guardian and other full members (four in A: bob, cara, dave and emma; two in B) and a `#general` group that all of them are in, and, in A, `#news` `CA0000NEWS1`, `#design` `CA0000DSGN1`, `#ops` `CA0000OPS01` and `#sales` `CA0000SALES`, which hold the bot, the guardian and the four members, so the bot is in five shared groups there, and `#quiet` `CA0000QUIET` (the bot and the guardian are not), each holding messages said before the app arrived (`seed_messages`, put back after a reset). `#news` holds three plain messages and a thread on `1700000000.000400` with two replies. The bot reads, reacts and posts only in groups it is in, as on Slack, and a search sees only what the searching user is in. There is also workspace C `TC0000CCCC` (Cobalt), with an owner and one full member, which belongs to nobody on the team and no instance signs in to. A is the app's home workspace, the one it was created in. Its public distribution is on by default (`FAKE_SLACK_DISTRIBUTED`, or `ctl.sh distribution on|off` while running); off, the approve screen refuses a workspace other than A with Slack's `invalid_team_for_non_distributed_app` and issues no code. Each workspace also has one guest, in no group: `UA0000GST01` and `UB0000GST01` are multi-channel guests (`is_restricted` on `users.info`), and C's `UC0000GST01` a single-channel guest (`is_ultra_restricted` too). `users.info` answers `team_id`, `is_restricted`, `is_ultra_restricted`, `is_bot` and `deleted` for everyone, and env.json lists each workspace's `full_members` (not the guardian) and `guests`. Any member or guest can send the bot a direct message, not only the one who signed in. The bot user in a workspace is always `UBOT` plus the team id without its `T`, and a member's direct message with the bot is always the same conversation id, listed by `GET /_control/state`. The app is installed in a workspace once a sign-in there finishes, and one workspace has one bot token, as in Slack. Removing the app (`/uninstall`) revokes the tokens and then sends `tokens_revoked` and `app_uninstalled`, so an app that checks its token on either event finds it revoked. A sign-in after that installs it again with a new bot token and the same bot user, and what was said before stays in Slack.

### Control API

All under `/_control`, JSON in and out.

| Call | What it does |
|---|---|
| `GET /health` | Answers `{ ok: true }`. |
| `GET /state` | The app's ids, the events address, the history limit, each workspace with its install, its bot token's state and scopes, bot ids, members with their direct-message conversation ids, and groups with their members. |
| `POST /sign-in {team, user}` | Picks who the approve screen signs in as. |
| `POST /dm {team, user, text, thread_ts?, send_event?}` | A member sends the bot a direct message. Sends a signed `message.im` event and returns `event_id`, the `event` (with `channel` and `ts`), and the first `delivery` (status, time taken). Refused with 409 if the app is not installed in that workspace, or lacks `im:history`. With `send_event: false` the message only enters the direct message's history, and the answer is `{event_sent: false, ts, event}`. A sent message answers `event_sent: true` and its `ts` too. |
| `POST /mention {team, user, channel?, text, thread_ts?}` | A member mentions the bot in a group (default `general`), or in a thread there: with `thread_ts` the event carries it, as Slack's does, and the message joins that thread. Sends a signed `app_mention` event, but only from a group the bot is in; elsewhere the message only enters the history. Answers `event_sent`, `ts` and the `event`, and `event_id` when sent. |
| `POST /group-message {team, user, channel?, text, thread_ts?, send_event?}` | A member writes in a group without mentioning the bot. It goes into the group's history only, because the app subscribes to no group message event; `send_event: true` also sends it as `message.channels`. With `thread_ts` it is a reply in that thread. Answers `event_sent`, `ts` and the `event`. |
| `POST /batch {items: [{kind, team, user, channel?, text, thread_ts?, send_event?}]}` | Several members write at the same moment. `kind` is `mention`, `dm` or `group-message`, and each item does what the single call of that name does. Every message takes its `ts` first, in the order given, and then every event goes out at once, so no delivery waits on another. Answers `results` in the items' order, each as the single call answers, with `kind` the event type. An unknown kind or member refuses the whole batch with 400 before anything is sent. |
| `GET /history?team&channel` | Everything kept in one conversation, oldest first, threads included, with no limit. |
| `POST /grant-limit {team, scopes}` | The only bot scopes a later sign-in from `team` grants, as a list or a comma-separated string; `null` lifts the limit. A sign-in under a limit leaves the install with the limited scopes only, as for a workspace that approved the app before it asked for more, so its calls that need another scope answer `missing_scope`. Lift it and sign in again to approve the rest. The install keeps its bot token. `GET /state` shows it as each workspace's `grant_limit`. |
| `POST /auth-test {team}` | Runs `auth.test` with the newest bot token issued in the workspace, unrecorded, and answers `token_state` (`active` or `revoked`) and Slack's answer. |
| `POST /forged {team, user, text, kind?, mode?}` | Sends a direct message (or, with `kind: "mention"`, a mention) that Slack did not sign. `mode` is `bad_signature` (default), `stale_timestamp` (signed, but 10 minutes old) or `missing_signature`. Forged events are not retried. |
| `POST /event {team, event, signature?}` | Sends any event body, signed unless `signature` names a forgery. |
| `POST /url-verification` | Sends Slack's `url_verification` challenge and returns what the address answered. |
| `POST /uninstall {team}` | Removes the app from a workspace: the workspace's tokens stop working, then it sends `tokens_revoked` and `app_uninstalled`. |
| `GET /posts?team&channel&thread_ts&since` | What was posted through `chat.postMessage`, oldest first, each with `seq`, `channel` (a group, or a member's direct message `D…`, also when the app named the member), `ts`, `threadTs` (null outside a thread), `text` and the token kind. |
| `GET /calls?team&method&since` | Every Web API call received, with secrets redacted. |
| `GET /events?since` and `GET /deliveries?event_id&since` | Every event sent, and every delivery attempt with its status. |
| `POST /redeliver {event_id, reason?}` | Slack's own retry of an event it sent: the stored envelope unchanged, under the same `event_id`, with `X-Slack-Retry-Num` one past the last attempt and `X-Slack-Retry-Reason` (`reason`, default `http_error`), signed again over a current timestamp. It answers with the delivery; an unknown `event_id` answers 404. |
| `POST /config {events_url?, retry_delays_ms?, history_limit?, history_window_ms?, self_events?, distributed?}` | Changes the events address, the retry delays, the history limit, whether the app hears of its own posts, or whether its public distribution is active, while running. |
| `POST /other-app {team, kind: socket_bot\|oauth, name?, scopes?, user_scopes?, installed_by?}` | Setup only. Installs another Slack app in a workspace, as an upgraded workspace would hold one: `socket_bot` is a guardian's own Socket Mode app (the `slack_bot` kind), with a bot token and an app-level token; `oauth` is Rome Cloud's earlier OAuth app (the old `slack` kind), with a bot token and the installer's user token. Answers the app's ids and its tokens. The same name in the same workspace answers the same app. `GET /state` lists them under `other_apps` without tokens. |
| `GET /sockets?since` and `POST /socket-event {app_id, event}` | Socket Mode: every connection opened, said hello to, sent to, acked and closed; and an Events API payload sent to an app over its open connection, answering whether it was acked. |
| `GET /tokens` | Test only: every token issued, `{value, team, kind, app, user, revoked}`. Values are this environment's own. |
| `GET /approvals?since` | Every answer on the approve screen: the workspace, the member, and whether it was `approved`, `cancelled` or `refused` (with Slack's error). |
| `POST /reset {installs?, history?}` | Clears the records. Keeps installs and tokens unless `installs` is true, and what was said unless `history` is true. |

Every record carries a `seq` from one counter, and each list answers with the current `seq`, so a test reads "everything since" by passing the `seq` it saw before acting.

## Live mode (real Slack, on the devbox)

`live.sh` runs Rome Cloud and one Rome instance against the real Slack, apart from everything above: its own compose project (`slackenv-live`, `live/compose.yml`), state folder (`.state-live`), image tag (`slackenv-live-rome:<sha>`) and no published port. Nothing in it changes how `up.sh` runs.

```sh
environments/slack-app/live.sh up --rome origin/<branch> --rome-cloud origin/<branch> [--slug slack] [--guardian <email>]
environments/slack-app/live.sh check   # Slack's signed URL challenge, through Traefik and through the public name
environments/slack-app/live.sh down    # containers, volumes, state and scratch worktrees; --images removes the image too
```

- Names. Rome Cloud is `https://<slug>-pantheon.romeos.dev` and the instance's dashboard `https://<slug>.romeos.dev` (default slug `slack`). The devbox's tunnel and Caddy shim send those as `pantheon.<slug>.rome.localhost` and `<slug>.rome.localhost` to the singleton `rome-traefik` on `127.0.0.1:3000`, and Traefik finds the two containers by their labels on the `rome-edge` network. `up` refuses a slug another stack already routes, or one the shim reserves.
- Inside the network, the same names answer through `tools/tls-proxy.mjs` with the environment's own certificate, so the instance's calls to Rome Cloud and Rome Cloud's calls back never pass Cloudflare Access.
- Rome's Slack app comes from `SLACK_APP_CLIENT_ID`, `SLACK_APP_CLIENT_SECRET` and `SLACK_APP_SIGNING_SECRET` in the environment, or else `~/.config/rome/slack-app.env`. They reach only Rome Cloud's container, through compose's interpolation when it is created, and no file this environment writes. `SLACK_APP_BASE_URL` is unset, so Rome Cloud talks to slack.com.
- Sign-in. Rome Cloud runs its dev sign-in, behind Cloudflare Access. `up` enrolls the instance as the guardian account (`--guardian`, default `guardian@slackenv.test`) and prints the sign-in link for that account.
- Cloudflare. Slack posts events without an Access login, so the Access app needs a Bypass policy for `<slug>-pantheon.romeos.dev/api/slack/events`. The OAuth callback is a browser redirect and needs none. `check` says which leg fails: Traefik, the signature, or Access.
