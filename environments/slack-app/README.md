# Slack app test environment

Everything the official Slack app and its verifier need to run with no person present: a fake Slack, Rome Cloud and the webhook relay, and two Rome instances enrolled in that Rome Cloud. The rules it serves are in the project's rule set (R1, R3, R4, R6, R7, R11 in phase 1). How it differs from production is in [DIFFERENCES.md](DIFFERENCES.md).

## Start and stop

```bash
environments/slack-app/up.sh --rome <ref> --rome-cloud <ref>   # default origin/main for both
environments/slack-app/ctl.sh stop rome-a                       # and start, status; logs <service>
environments/slack-app/ctl.sh wipe-chat rome-a DA000A0000BOB01      # wipe Rome's copy of one chat
echo 'select count(*) from users' | environments/slack-app/ctl.sh cloud-query
environments/slack-app/down.sh                                  # removes containers, volumes and .state
```

`up.sh` needs Docker with Compose, Node 22 or later and git. It finds the rome-cloud checkout at `$ROME_CLOUD_DIR`, else next to this rome checkout. It needs one model credential, `SLACKENV_ANTHROPIC_API_KEY` or `SLACKENV_CLAUDE_OAUTH_TOKEN` (or the files `~/.config/slackenv/anthropic-api-key`, `~/.config/slackenv/claude-oauth-token`), which only the model proxy holds. `--cloud-only` starts everything but the instances and needs no credential.

It runs only committed code. It refuses to start when this folder has uncommitted changes, and it checks rome and rome-cloud out at the given commits into fresh worktrees under `.state/`, so nothing uncommitted in either checkout reaches the environment. The first start of a rome commit builds its production image, which takes several minutes.

When it is ready it writes `.state/env.json` (gitignored): the scratch checkouts of rome (with its dependencies installed, so `pnpm lint:imports` runs there) and rome-cloud, the rome-cloud base ref to diff against, the commits of the environment, rome and rome-cloud, the agent model, the fake Slack's address and control API, Rome Cloud's address, Rome Cloud's read-only query command, and each instance's address, guardian, signed-in guardian session, and its controls (stop, start, status, wipe_chat).

## Controls

- `ctl.sh wipe-chat <instance> <conversation id>` wipes Rome's copy of one Slack conversation, which the product offers no way to do. It stops the instance, runs `tools/wipe-chat.mjs` on its database in the instance's image, and starts the instance again if it was running. Gone afterwards: the Slack app connection's own copy (`slack_app_messages`), the chat's messages (`chat_messages`), the chat's conversations with Rome's agents (`rome_sessions` of the chat and their sub-sessions, with their messages, traces, outputs and per-message rows), and the agent provider sessions of those conversations with their transcripts on disk, so the next message starts a model thread that knows nothing of the old. The chat's place and address stay, and so do the connection and memory. Then, in every other table, it deletes each row whose text holds the conversation id or a wiped message's text (plain or JSON-escaped), so copies in approvals, action runs and later Slack app connection tables such as `slack_app_timeline` go too. A conversation the sweep took a message from, such as a dashboard chat that quoted the words, also loses its agent provider sessions and their transcripts, and they are listed in `provider_sessions`. Last, it searches every text column again and prints JSON with what it deleted (`deleted`), what still holds content (`remaining`), and the places that name the conversation but hold no message (`kept`, which can list only the `chats` and `chat_addresses` tables; the top-level `chats` is the list of wiped chat ids). `deleted` counts rows per table. `remaining` and `kept` count, per table and column, the rows whose column holds the conversation id or a wiped text, so a row that holds them in two columns is counted under each. It exits 0 when `remaining` is empty, 3 when it is not. `ctl.sh wipe-chat <instance> <conversation id> --text <text> [--text <text>]...` also removes what Rome distilled from the chat, such as a fact the Concierge saved to memory: every row in any table that holds one of the texts (plain or JSON-escaped), and in every text file under the instance's homes (the memory folder included) each line that holds one, a file left empty going too. A transcript (`.jsonl`) that holds one goes whole, with its provider session. Each text must be 8 characters or more, so it cannot match an id or a hash. Those lines are counted under `deleted["(files)"]`, and a file still holding a text is listed under `remaining["(files)"]` by path. Without `--text`, the wipe is as above. History in a git repository (a profile's `.git`) is not rewritten or searched.
- `ctl.sh token-file <instance>` prints whether the instance holds `/run/rome/slack-oauth-token`, the file the connector app reads its Slack tokens from, and the last 6 characters of the bot and user tokens in it.
- `ctl.sh old-connections <instance>` gives the instance the two older Slack connections an upgrade from main leaves, for R10: a guardian's own Socket Mode bot (`slack_bot`) and Rome Cloud's earlier OAuth app (`slack`), both in the guardian's workspace (Acme for rome-a, Bayside for rome-b). It stops the instance, and in the instance's image installs both apps in the fake Slack and writes the rows main writes into its database, so the tokens never leave that process (`tools/old-connections.mjs`; DIFFERENCES.md lists them), starts it again, and links the bot to the Concierge. It prints each connection's `connection_id`, `account_id`, `app_id` and `bot_user_id` with its checks, saves them to `.state/<instance>-old-connections.json` (no tokens), and exits 0 when rome lists both, the bot's Socket Mode connection is open and the OAuth tokens are in the token file. Run again, it keeps the connections it wrote. `up.sh --old-connections <instance>` runs it before env.json is written, which then lists them under the instance.
- `ctl.sh product-tests <file>...` runs test files of the rome commit under test, unchanged, for R9's existing tests. Paths are repo-relative. The first call for a commit builds `slackenv-rome-test:<commit>` from a `git archive` of `.state/rome-src` with `test-runner/Dockerfile` (a full `pnpm install --frozen-lockfile`, several minutes); later calls reuse it. Each file runs, with no network, in the package whose rstest config takes it (`rome_apps/*` under `packages/core`), as `scripts/test-env.sh rstest run`. It prints rstest's output, then a last line `{ok, commit, runs: [{package, files, exit_code}], error?}`, and exits 0 when every run passes, 2 when a file is not in the commit, 126 when the test image lacks a file (the runner cannot check it), otherwise the first failing run's code. The image keeps the test files: `test-runner/Dockerfile.dockerignore` takes the place of rome's own `.dockerignore`, which leaves them out of the instance image.
- `browser` (a compose service) is Playwright's image at the version rome pins, serving `playwright run-server` on the host's network at `127.0.0.1:47190`, so the verifier drives a browser without installing one. `up.sh` installs the matching `playwright-core` client into `.state/browser-client`. env.json `browser` names the endpoint and the client: `(await import(browser.import)).chromium.connect(browser.ws_endpoint)`. `down.sh --images` also removes the test images.
- `ctl.sh distribution on|off` turns the app's public distribution on or off in the fake Slack.
- `ctl.sh cloud-query` reads one SELECT (or WITH) query on stdin and prints its rows as a JSON array. It runs as `slackenv_reader`, a role that can only read, inside a read-only transaction.

## What runs

| Service | Address | What it is |
|---|---|---|
| `fake-slack` | `http://127.0.0.1:47200`, and `https://slack.com` inside the network | The fake Slack, below |
| `pantheon` | `http://127.0.0.1:47100` | Rome Cloud from the given rome-cloud commit, `next dev`, with its own Postgres. Slack's events go to `/api/slack/events`. |
| `relay` | `http://relay:8787` inside the network | The webhook relay from the given rome-cloud commit, unmodified, under `wrangler dev` |
| `rome-a`, `rome-b` | `http://127.0.0.1:47181`, `:47182` | Rome from the given rome commit's production image, each with its signer, enrolled in Rome Cloud with the Concierge on. Guardians `guardian-a@slackenv.test` and `guardian-b@slackenv.test`. |
| `model-proxy` | inside the network | Pins every model request to Haiku 5.5 and adds the credential |

Each instance and Rome Cloud run inside the network namespace of a small forwarder (`tools/forward.mjs`) that maps the same loopback ports to Rome Cloud and the fake Slack. So `http://127.0.0.1:47100` names Rome Cloud and `http://127.0.0.1:47200` names the fake Slack on the host, in a browser, and inside every container alike, and the sign-in redirects work without host name tricks.

[DIFFERENCES.md](DIFFERENCES.md) lists every way this differs from production.

## Fake Slack

`fake-slack/server.mjs` stands in for `slack.com`. It has no dependencies and runs on Node 22 or later. Its tests, and those of the tools, run with `node --test environments/slack-app/fake-slack/*.test.mjs environments/slack-app/tools/*.test.mjs`. The wipe's test builds a database from Rome's migrations; `ROME_SRC=<rome checkout>` picks whose (by default this checkout's).

It serves:

- the approve screen, `GET /oauth/v2/authorize`, with the usual `client_id`, `scope`, `user_scope`, `redirect_uri` and `state`. Pressing Allow redirects to `redirect_uri` with `code` and `state`. Pressing Cancel redirects with `error=access_denied`. Optional `team` and `user` query parameters pick the workspace and the member signing in, and so does `POST /_control/sign-in`.
- Socket Mode for another app's app-level token: `apps.connections.open` answers `wss://wss-primary.slack.com/link/?ticket=…`, which the fake serves (that name is in its certificate and the network), saying `hello` and taking an ack per envelope. An app-level token can call nothing else, and a bot token cannot open it (`not_allowed_token_type`).
- the Web API under `/api/{method}`: `apps.connections.open`, `oauth.v2.access`, `auth.test`, `auth.revoke`, `chat.postMessage`, `conversations.open`, `conversations.list`, `conversations.info`, `conversations.history`, `conversations.replies`, `users.info`, `users.list`, `reactions.add` and `search.messages`. Arguments come as a form, JSON or a query, and the token as `Authorization: Bearer` or `token`. Unknown methods answer `unknown_method`. Every call is recorded, a refused one with its error.
- scopes, as Slack checks them: a bot token holds the scopes the install's sign-ins asked for, a user token the user scopes of its own sign-in, and a method the token lacks the scope for answers `missing_scope` with `needed` and `provided` (`chat.postMessage` needs `chat:write`, `conversations.open` `im:write`, `users.info` and `users.list` `users:read`, `reactions.add` `reactions:write`, `search.messages` `search:read`, `conversations.list` and `conversations.info` `channels:read`, `groups:read`, `im:read` or `mpim:read` for each kind of conversation asked for, and a history read `im:history`, `channels:history` or `groups:history` by the kind of conversation). `search.*` answers a bot token `not_allowed_token_type`. Each recorded call carries its `tokenKind`, the `scopes` the token held, and `needed` when it was refused for one. Slack sends no event the install lacks the scope for: `message.im` needs `im:history` and `app_mention` `app_mentions:read`, and the control call that would send it answers 409. `users.info` leaves a member's `profile.email` out unless the install holds `users:read.email`.
- the app's own posts in a direct message, sent back to it as a signed `message.im` event with its `bot_id` and bot user, right after `chat.postMessage` answers, as Slack does. An app must ignore them. `POST /_control/config {self_events: false}` stops them.
- what was said. Every direct message, mention, group message and post is kept in its conversation, with threads: a reply carries `thread_ts`, and its parent `reply_count`, `reply_users` and `latest_reply`. `conversations.history` answers a conversation's top-level messages newest first, and `conversations.replies` a thread oldest first with the parent at the top. Both take `limit`, `cursor`, `oldest`, `latest` and `inclusive`, and answer `has_more` and `response_metadata.next_cursor`.
- Slack's limit for an app outside the Marketplace on those two methods, on by default: one request a minute per method and workspace, at most 15 messages a request (also the default), and HTTP 429 `ratelimited` with `Retry-After` beyond that. `POST /_control/config {history_limit: false}` lifts it to Slack's ordinary page size (default 100, at most 999) with no rate limit.
- events, posted to the configured events address and signed as Slack signs them: `X-Slack-Request-Timestamp` and `X-Slack-Signature: v0=` HMAC SHA256 of `v0:{timestamp}:{body}` with the signing secret. An event that gets no 2xx is retried with `X-Slack-Retry-Num` and `X-Slack-Retry-Reason`.

The workspaces and their members are in `config/workspaces.json`: workspace A `TA0000AAAA` (Acme) and workspace B `TB0000BBBB` (Bayside), each with a guardian, two other members and a `#general` group that all three are in, and, in A, `#news` `CA0000NEWS1` (the bot is in it) and `#quiet` `CA0000QUIET` (the bot and the guardian are not), each holding one message said before the app arrived (`seed_messages`, put back after a reset). The bot reads, reacts and posts only in groups it is in, as on Slack, and a search sees only what the searching user is in. There is also workspace C `TC0000CCCC` (Cobalt), with an owner and one member, which belongs to nobody on the team and no instance signs in to. A is the app's home workspace, the one it was created in. Its public distribution is on by default (`FAKE_SLACK_DISTRIBUTED`, or `ctl.sh distribution on|off` while running); off, the approve screen refuses a workspace other than A with Slack's `invalid_team_for_non_distributed_app` and issues no code. Any member can send the bot a direct message, not only the one who signed in. The bot user in a workspace is always `UBOT` plus the team id without its `T`, and a member's direct message with the bot is always the same conversation id, listed by `GET /_control/state`. The app is installed in a workspace once a sign-in there finishes, and one workspace has one bot token, as in Slack. Removing the app (`/uninstall`) revokes the tokens and then sends `tokens_revoked` and `app_uninstalled`, so an app that checks its token on either event finds it revoked. A sign-in after that installs it again with a new bot token and the same bot user, and what was said before stays in Slack.

### Control API

All under `/_control`, JSON in and out.

| Call | What it does |
|---|---|
| `GET /health` | Answers `{ ok: true }`. |
| `GET /state` | The app's ids, the events address, the history limit, each workspace with its install, its bot token's state and scopes, bot ids, members with their direct-message conversation ids, and groups with their members. |
| `POST /sign-in {team, user}` | Picks who the approve screen signs in as. |
| `POST /dm {team, user, text, thread_ts?, send_event?}` | A member sends the bot a direct message. Sends a signed `message.im` event and returns `event_id`, the `event` (with `channel` and `ts`), and the first `delivery` (status, time taken). Refused with 409 if the app is not installed in that workspace, or lacks `im:history`. With `send_event: false` the message only enters the direct message's history, and the answer is `{event_sent: false, event}`. |
| `POST /mention {team, user, channel?, text, thread_ts?}` | A member mentions the bot in a group (default `general`), or in a thread there. Sends a signed `app_mention` event, but only from a group the bot is in; elsewhere the message only enters the history and the answer says `event_sent: false`. |
| `POST /group-message {team, user, channel?, text, thread_ts?, send_event?}` | A member writes in a group without mentioning the bot. It goes into the group's history only, because the app subscribes to no group message event; `send_event: true` also sends it as `message.channels`. |
| `GET /history?team&channel` | Everything kept in one conversation, oldest first, threads included, with no limit. |
| `POST /auth-test {team}` | Runs `auth.test` with the newest bot token issued in the workspace, unrecorded, and answers `token_state` (`active` or `revoked`) and Slack's answer. |
| `POST /forged {team, user, text, kind?, mode?}` | Sends a direct message (or, with `kind: "mention"`, a mention) that Slack did not sign. `mode` is `bad_signature` (default), `stale_timestamp` (signed, but 10 minutes old) or `missing_signature`. Forged events are not retried. |
| `POST /event {team, event, signature?}` | Sends any event body, signed unless `signature` names a forgery. |
| `POST /url-verification` | Sends Slack's `url_verification` challenge and returns what the address answered. |
| `POST /uninstall {team}` | Removes the app from a workspace: the workspace's tokens stop working, then it sends `tokens_revoked` and `app_uninstalled`. |
| `GET /posts?team&channel&thread_ts&since` | What was posted through `chat.postMessage`, oldest first, each with `seq`, `channel`, `ts`, `threadTs`, `text` and the token kind. |
| `GET /calls?team&method&since` | Every Web API call received, with secrets redacted. |
| `GET /events?since` and `GET /deliveries?event_id&since` | Every event sent, and every delivery attempt with its status. |
| `POST /config {events_url?, retry_delays_ms?, history_limit?, history_window_ms?, self_events?, distributed?}` | Changes the events address, the retry delays, the history limit, whether the app hears of its own posts, or whether its public distribution is active, while running. |
| `POST /other-app {team, kind: socket_bot\|oauth, name?, scopes?, user_scopes?, installed_by?}` | Setup only. Installs another Slack app in a workspace, as an upgraded workspace would hold one: `socket_bot` is a guardian's own Socket Mode app (the `slack_bot` kind), with a bot token and an app-level token; `oauth` is Rome Cloud's earlier OAuth app (the old `slack` kind), with a bot token and the installer's user token. Answers the app's ids and its tokens. The same name in the same workspace answers the same app. `GET /state` lists them under `other_apps` without tokens. |
| `GET /sockets?since` and `POST /socket-event {app_id, event}` | Socket Mode: every connection opened, said hello to, sent to, acked and closed; and an Events API payload sent to an app over its open connection, answering whether it was acked. |
| `GET /approvals?since` | Every answer on the approve screen: the workspace, the member, and whether it was `approved`, `cancelled` or `refused` (with Slack's error). |
| `POST /reset {installs?, history?}` | Clears the records. Keeps installs and tokens unless `installs` is true, and what was said unless `history` is true. |

Every record carries a `seq` from one counter, and each list answers with the current `seq`, so a test reads "everything since" by passing the `seq` it saw before acting.
