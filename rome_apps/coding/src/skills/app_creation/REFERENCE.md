# Rome Apps Development Reference

This document is the **file-level API lookup**. It is the companion to
[`AUTHORING.md`](./AUTHORING.md) — AUTHORING covers *workflow and what to
build* (iteration loop, design rules, validation, delivery); this file covers
*how to type each piece* (file layouts, yaml fields, SDK functions, schema
patterns).

For more public, end-to-end examples, see
[`amantru/rome-apps`](https://github.com/amantru/rome-apps). Each app in that
repo is a self-contained, readable sample covering different shapes:
action / agent / api / web / db / hook.

---

## App Layout & File Meanings

A complete Rome app has the following root layout (not every file is required
— see SKILL.md's "delete what your app does not need" rule):

```
<app-root>/
├── app.yaml                    # App manifest (required)
├── README.md                   # App Store readme body (product copy, not technical)
├── .rome_store/
│   ├── rome_store.yaml         # Rome Cloud store metadata sidecar
│   └── assets/                 # Store-only images / videos
├── package.json                # Runtime + dev deps
├── tsconfig.json               # TypeScript config
├── drizzle.config.ts           # DB migration config (only if DB is enabled)
├── components.json             # shadcn CLI config, for the rare copied recipe (web UI only)
└── src/
    ├── actions/<name>/         # One directory per action
    │   ├── action.yaml         # Public action contract
    │   ├── index.ts            # Implementation
    │   └── index.test.ts       # Tests (recommended)
    ├── agents/<name>.yaml      # App-private agent definitions
    ├── skills/<name>/SKILL.md  # Skills the agent can pick up
    ├── hooks/<name>/           # Channel / event hooks (e.g. channel-message)
    ├── api/index.ts            # Entry for /api/apps/<appId>/...
    ├── db/
    │   ├── schema.ts           # Drizzle table definitions
    │   ├── migrations/         # Generated by drizzle-kit
    │   └── repositories/       # Repository-pattern wrappers
    └── web/
        ├── App.tsx             # Web entry; default-exports a React component
        ├── styles.css          # @imports the SDK token layer + app-specific rules
        ├── components/ui/      # ONLY primitives @rome-os/ui does not publish
        └── lib/utils.ts        # re-exports `cn` from @rome-os/ui/cn
```

Build output lives in `dist/`, produced by `rome build`. **Never edit `dist/`
by hand** — the daemon loads from `dist/`, not `src/`.

### `app.yaml`

The app manifest. Declares every public piece of metadata and every artifact
the app ships. The daemon reads this on `install` to register components.

```yaml
formatVersion: 2                 # Required for new apps; v1 is read only for compatibility
id: coding                       # Required, globally unique — lowercase-hyphenated machine id (paths/URLs/table prefix)
name: Coding                     # Display name — Title Case words ("Morning Brief"), never the kebab id
icon: assets/icon.svg            # Optional
version: 0.2.8                   # Semantic version
description: Short description
appRoot: dist                    # Optional; defaults to source root if omitted
includeSource: true              # Optional; publish src/ with the Store bundle
remix:                            # Rome-managed lineage for a derived app
  listing: "@alice/calendar"
  version: 1.2.3

web:                             # Optional — enables the web UI
  manifest: web/manifest.json    # rslib output manifest
  displayName: Coding            # Title Case, like `name`
  navLabel: Coding               # Title Case, like `name`

api:                             # Optional — enables the HTTP API
  entry: api/index               # Without extension

agents:                          # Optional — app-private agents
  - agents/planning.yaml
  - agents/coding.yaml

actions:                         # Optional — action directories the app exposes
  - actions/coding-task

skills:                          # Optional — skill directories the app ships
  - skills/app_creation

hooks:                           # Optional — runtime hooks
  - hooks/channel-message
```

**Rule:** validation is strict — unknown fields in `app.yaml`, `action.yaml`,
and agent yaml are rejected at pack/install. New apps use `formatVersion: 2`;
version 1 remains readable only for legacy bundles.

Agent, action, and skill definitions use app-local names matching
`^[a-z][a-z0-9_-]{0,63}$`. A definition name must never contain `:`. References
use canonical `<app-id>:<local-name>` ids for both same-app and cross-app
targets. For example, in an app whose id is `review-app`:

```yaml
# agents/reviewer.yaml
name: reviewer
actions: [review-app:review]
allowedSubagents: [review-app:researcher, assistant:explore]
```

Only declare fields documented here.

### Canonical artifact ids

Artifact definitions declare an app-local `name`; references and runtime calls
always use the canonical `<app-id>:<local-name>` id. This applies to same-app
references too. Never write a bare artifact reference and never use
`self:<local-name>`. Store listing ids are unrelated to runtime artifact ids.
An app should also include its `appId` when using its own agent, action, or skill.

Use these fixed ids instead of guessing the owner of a platform artifact:

| Purpose | Canonical id |
|---|---|
| App lifecycle and scaffolding | `system:app_management` |
| Run another agent | `system:summon` |
| Create/delete a routine | `system:create_routine`, `system:delete_routine` |
| Send a message / read channel history | `system:send_message`, `system:fetch_channel_history` |
| Publish/search event types | `system:publish_event`, `system:search_event_catalog` |
| Call a connected provider API | `connector:connector_proxy` |
| Core agents | `core:main`, `core:envoy` |
| General-purpose agents | `assistant:assistant`, `assistant:explore` |
| Coding agents | `coding:planning`, `coding:coding` |
| App authoring skills | `coding:app_creation`, `coding:workflow_creation`, `coding:app_remix`, `coding:app_verification` |

For an app whose id is `notes`, an action definition is `name: notes_create`,
while its allowlist entry, routine target, and `runAction` input are all
`notes:notes_create`.

The app templates set `includeSource: true`. This publishes `src/` in the same
Store bundle as the runtime artifact. Set it to `false` to keep source out of
future versions. A manifest without the field uses the legacy no-source behavior.

`app_remix` writes `remix` when it creates a derived app. It records the exact
Store listing and version copied into the new source tree. Do not edit this
field to point at a different source.

**Rule:** every directory listed in `app.yaml` must actually exist on disk.
When you remove a capability, delete the directory **and** its matching
`app.yaml` entry together — leaving one without the other fails `install`
validation.

Store-page metadata is intentionally outside `app.yaml`. Put Rome Cloud listing
fields in `.rome_store/rome_store.yaml`; publish uploads `.rome_store` as a
sidecar and excludes it from installable app bundles.

```yaml
title: Morning Brief
description: Daily calendar, inbox, and reminder summaries.
long_description: |
  A richer store description with room for product copy.
categories:
  - Productivity
keywords:
  - daily briefing
  - calendar assistant
image: assets/store-og.png
image_alt: Morning Brief preview
media:
  - type: image
    path: assets/dashboard.png
    alt: Morning Brief dashboard
noindex: false
```

Store asset paths are relative to `.rome_store/`, so the example above expects
files under `.rome_store/assets/`.

### `action.yaml`

Declares an action's metadata. The agent planner reads it when deciding
whether to pick this action.

```yaml
name: dream                  # Action name; this is what agents call
type: custom                 # Almost always `custom`
description: Concise summary # The agent sees this — write it clearly
entry: ./index.ts            # Optional; defaults to ./index.ts
complexity: simple|moderate|complex   # Call cost
speed: fast|moderate|slow
reliability: low|medium|high
sideEffects: read-only|write # IMPORTANT: write may trigger approval policies
```

### `agents/<name>.yaml`

App-private agent definitions. App agents can only be invoked from inside the
app (e.g. via `system:summon` or `agentRunner.run`). This example belongs to an
app whose id is `research-app`:

```yaml
name: dream
description: Short description
tier: medium                   # Capability tier: large | medium | small
reasoningEffort: high          # Optional: low | high | xhigh; defaults to high
systemPromptPrefix: |
  Multi-line system prompt.
tools:                         # Built-in tool allowlist
  - Read
  - Write
  - Edit
  - Grep
  - Glob
actions:                       # Action allowlist; "*" opens everything
  - research-app:notes_create
  - system:fetch_channel_history
allowedSubagents:              # Optional: canonical ids this agent may run through `system:summon`
  - assistant:explore
permissionMode: acceptEdits    # File-edit permission: acceptEdits | bypassPermissions | default
maxTurns: 30                   # Optional: maximum conversation turns; recommended >= 30
```

`tier` is a provider-agnostic capability tier. The daemon maps it to a
concrete model based on the current provider.

`reasoningEffort` is independent of `tier` and controls how much reasoning the
selected model should use. It accepts `low`, `high`, or `xhigh` and defaults to
`high` when omitted.

#### Structured output: `outputSchema`

When you want the agent to return **structured JSON** rather than free-form
text, declare an `outputSchema`. Rome passes the schema to the selected
provider's native structured-output API. The provider returns one schema-valid
terminal value or fails the turn.

```yaml
name: sentinel
description: Triages incoming messages from untrusted senders
tier: small
permissionMode: bypassPermissions
tools: [Read, Glob, Grep]
actions: ["*"]
outputSchema:
  type: object
  required: [decision, reason]
  additionalProperties: false
  properties:
    decision:
      type: string
      enum: [REPLY, ESCALATE, IGNORE]
    reason:
      type: string
systemPromptPrefix: |
  You are a triage agent. For each message decide REPLY / ESCALATE / IGNORE.
  Return your decision and reasoning as the final structured result.
```

While iterating `agentRunner.run()`, callers read the validated payload from
the terminal `result`:

```ts
for await (const msg of agentRunner.run({ agentName: "research-app:sentinel", prompt })) {
  if (msg.type === "result" && msg.structuredOutput) {
    const { decision, reason } = msg.structuredOutput as {
      decision: string;
      reason: string;
    };
    // `decision` is guaranteed to be one of REPLY | ESCALATE | IGNORE
  }
}
```

### `skills/<name>/SKILL.md`

A skill is a "natural-language capability fragment" addressed at agents.
Frontmatter + Markdown body:

```markdown
---
name: app_creation
description: One sentence on when to use this skill
tools: [Read, Edit, Bash]
---

# Title
Body. The agent reads this and follows the workflow described inside.
```

The `description` **must** state the trigger condition — the agent uses it to
decide whether to load the skill.

### `package.json`

```jsonc
{
  "name": "@rome-app/<appId>",
  "type": "module",
  "scripts": {
    "build": "rome build",
    "dev": "rome dev",
    "db:generate": "drizzle-kit generate"
  },
  "dependencies": {
    // Step 3 of the scaffold flow runs `pnpm add <pkg>@latest` for each of
    // these, so a new app opens on the current release. Read the range from
    // your own package.json — never copy one out of a doc.
    //
    // ⚠️ Editing one by hand: keep it a concrete caret range.
    //   - NEVER "workspace:*" — apps install from npm on user machines;
    //     the workspace protocol does not resolve outside a monorepo.
    //   - NEVER "latest" — it silently pulls whatever the registry returns
    //     at install time, which breaks reproducibility and can ship a
    //     breaking SDK change to users without warning.
    "@rome-os/app-runtime": "<the release pnpm resolved>",
    "@rome-os/app-web-sdk": "<the release pnpm resolved>",
    // The component kit, when the app has a web UI. `pnpm up @rome-os/ui`
    // is how an app takes component fixes ("--latest" to cross a 0.x minor).
    "@rome-os/ui": "<the release pnpm resolved>"
  }
}
```

### The `rome` CLI

`rome` is the app build CLI shipped by `@rome-os/app-web-sdk`. From `<app-root>`:

| Command | What it does |
| --- | --- |
| `rome build` | Production build. Compiles `src/{api,actions,db,agents,skills,hooks,lib,docs}` with `tsc` into `dist/`, then bundles `src/web/App.tsx` with rslib into `dist/web/` (with `manifest.json`). A `mode: "source"` install runs this for you — run it directly only to catch build errors before installing. |
| `rome dev`   | Dev server with HMR for the web bundle. Use during heavy UI iteration; otherwise a single `install` (which rebuilds + repacks) is fine. |

Both commands read `app.yaml` for `web.displayName`, `web.navLabel`, and `web.entry` (default `App.tsx`). The web entry must default-export a React component — see [Frontend SDK](#frontend-sdk--rome-osapp-web-sdk).

## Backend SDK: `@rome-os/app-runtime`

The backend runtime SDK is the entry point for all backend code (actions,
hooks, API handlers).

### Actions: `createAction(config, deps)`

An action implementation file must `export function createAction(config, deps)`
(you can also export a named factory in addition; see the worked example in
[Actions calling actions / agents](#actions-calling-actions--agents)).

```ts
import type {
  Action,
  ActionConfig,
  ActionResult,
  AppActionRuntimeDeps,
} from "@rome-os/app-runtime";

export function createAction(
  config: ActionConfig,
  deps: AppActionRuntimeDeps,
): Action {
  return {
    config,
    inputSchema: {
      type: "object",
      properties: {
        prompt: { type: "string", description: "..." },
      },
      required: ["prompt"],
    },
    async execute(args): Promise<ActionResult> {
      // Business logic
      return { status: "ok", data: { /* ... */ } };
    },
  };
}
```

**Key types**

| Type | Purpose |
|---|---|
| `Action` | Shape of the returned object: `{ config, inputSchema?, execute }` |
| `ActionConfig` | Parsed from `action.yaml` and passed through at runtime |
| `ActionResult` | `{ status: "ok", data?: unknown } \| { status: "error", error: string } \| { status: "pending_approval", approval } \| { status: "pending_interaction", interaction }` |
| `AppActionRuntimeDeps<T>` | Dependency container; generic `T` is app-defined extras |

**Commonly used fields on `AppActionRuntimeDeps`**

- `appContext.runAction(canonicalId, args, options?)` — call another action (your own,
  another app's, or a platform action such as `system:summon` or
  `system:create_routine`; see [Creating routines](#creating-routines-systemcreate_routine)). This is the only
  way to invoke actions, and it is transport-blind: the runtime decides whether
  the callee runs in-process or in a worker, and your code observes the same
  behavior either way. `args` and `result.data` cross the call with JSON
  semantics (a `Date` arrives as an ISO string, `undefined` fields are dropped,
  no shared references). A failed invocation rejects with
  `ActionInvocationError` (`{ actionName, code, message }`, `code` one of
  `not_found | unserializable | handler_error | worker_failure`); an action
  that *ran* but declined still resolves with `{ status: "error", error }`.
  The default (`detached: false`) is a nested call and **must be awaited**;
  never use `void appContext.runAction(...)`. Use `{ detached: true }` only
  when the callee must become an independent root execution. Awaiting that
  form returns `{ executionId }` after main accepts it, not the action result.
- `appContext.listRoutines()` — list registered routines.
- `agentRunner.run({ agentName, prompt })` — stream-run an agent; returns
  an async iterable of `AgentMessage`. Handle each message by `msg.type`.
  Full example in
  [Actions calling actions / agents](#actions-calling-actions--agents).

  The stream's event vocabulary has three categories:

  | Category | Types | Semantics |
  | --- | --- | --- |
  | Lifecycle | `turn_start`, `turn_end`, `session_init` | Bracketing: `turn_start` (`turnId`, `sessionId`, `userPrompt`) precedes all content; `turn_end` (`turnId`, `status`, `durationMs`) is the stream's last event. `session_init` describes the session. |
  | Content | `thinking`, `text`, `tool_use`, `tool_result`, `structured_output`, `result`, `error` | Durable blocks. `structured_output` is reserved for interactive handback submissions. `result`/`error` is the agent's terminal block (at most one per agent per turn); `result.structuredOutput` carries provider-native structured data and `accounting` carries provider usage. |
  | Transient | `text_delta` | Streaming preview of an in-flight `text` block; never persisted — ignore unless you render live text. |

  Typical consumption: read `sessionId` from `turn_start` (to resume the
  session later), accumulate or forward content blocks, and take the final
  answer from `result.content`.

**Custom deps:** widen the factory signature with
`AppActionRuntimeDeps<MyDeps>` and inject them from the app's backend
bootstrap.

### APIs: `createApiHandler(ctx)`

The HTTP API module (`src/api/index.ts`) must
`export function createApiHandler(ctx)`. The daemon mounts requests at
`/api/apps/<appId>/[[...route]]`.

```ts
import type {
  RomeAppApiHandler,
  RomeAppApiRequest,
  RomeAppContext,
} from "@rome-os/app-runtime";

class MyApiHandler implements RomeAppApiHandler {
  constructor(private readonly ctx: RomeAppContext) {}

  async handle(request: RomeAppApiRequest): Promise<Response> {
    const route = request.path.join("/");

    // 1) GET /api/apps/<appId>/status — simple read
    if (request.method === "GET" && route === "status") {
      return Response.json({
        appId: this.ctx.app.id,
        version: this.ctx.app.version,
      });
    }

    // 2) GET /api/apps/<appId>/notes?limit=20&cursor=abc — query params
    //    `request.query` is a `URLSearchParams` instance. Read values with
    //    `.get(key)` (first value, or null) and `.getAll(key)` (all values
    //    for repeated keys).
    if (request.method === "GET" && route === "notes") {
      const limit = Number(request.query.get("limit") ?? "20");
      const cursor = request.query.get("cursor") ?? undefined;
      // Repeated keys: /notes?tag=foo&tag=bar -> ["foo", "bar"]
      const tags = request.query.getAll("tag");
      // `runAction` returns `ActionResult` — narrow on `status` and unwrap `.data`.
      const result = await this.ctx.runAction("notes:notes_list", { limit, cursor, tags });
      if (result.status !== "ok") {
        const error = result.status === "error" ? result.error : `notes_list returned ${result.status}`;
        return Response.json({ error }, { status: 500 });
      }
      return Response.json({ items: result.data });
    }

    // 3) GET /api/apps/<appId>/notes/:id — path parameter
    if (request.method === "GET" && request.path[0] === "notes" && request.path.length === 2) {
      const id = request.path[1];
      // ...look up by id
      return Response.json({ id });
    }

    // 4) POST /api/apps/<appId>/notes — JSON body write
    //    `request.body` is the raw request bytes as `Uint8Array | undefined`.
    //    The daemon does NOT parse JSON for you — decode and parse it yourself.
    if (request.method === "POST" && route === "notes") {
      const parsed = readJsonBody<{ title?: string; content?: string }>(request);
      if (!parsed.ok) {
        // Distinguish "no body" from "malformed body" so the client error
        // message is accurate.
        const error = parsed.reason === "empty" ? "request body required" : "invalid JSON body";
        return Response.json({ error }, { status: 400 });
      }
      const body = parsed.value;
      if (!body.title || !body.content) {
        return Response.json({ error: "title and content required" }, { status: 400 });
      }
      const result = await this.ctx.runAction("notes:notes_create", body);
      if (result.status !== "ok") {
        const error = result.status === "error" ? result.error : `notes_create returned ${result.status}`;
        return Response.json({ error }, { status: 500 });
      }
      return Response.json({ note: result.data }, { status: 201 });
    }

    return Response.json({ error: "not_found" }, { status: 404 });
  }
}

// Reusable helper — keep it next to your handler so every route shares it.
// Returns a discriminated result so callers can tell `empty body` from
// `unparseable JSON` and surface accurate error messages. NOTE: the parsed
// value is `as T` only — add a runtime schema check (zod, manual typeof,
// etc.) before trusting it on write paths.
type JsonBody<T> =
  | { ok: true; value: T }
  | { ok: false; reason: "empty" | "parse_error" };

function readJsonBody<T>(request: RomeAppApiRequest): JsonBody<T> {
  if (!request.body || request.body.byteLength === 0) {
    return { ok: false, reason: "empty" };
  }
  try {
    return { ok: true, value: JSON.parse(new TextDecoder().decode(request.body)) as T };
  } catch {
    return { ok: false, reason: "parse_error" };
  }
}

export function createApiHandler(ctx: RomeAppContext): RomeAppApiHandler {
  return new MyApiHandler(ctx);
}
```

**Key types**

- `RomeAppApiRequest` —
  `{ method, path: string[], headers: Record<string, string>, query: URLSearchParams, body?: Uint8Array, caller: RomeAppCaller }`.
  `path` has `/api/apps/<appId>/` stripped. `query` is a `URLSearchParams`
  instance — use `.get()` / `.getAll()`, not property access. `body` is the
  raw request bytes, **not** a pre-parsed object — decode with `TextDecoder`
  + `JSON.parse` for JSON, or hand the bytes to a binary parser for
  uploads.
- `request.caller` (`RomeAppCaller`, SDK ≥ 0.5.3) — host-resolved caller
  identity, the single trustworthy "who is calling" answer:
  `{ kind: "guardian"; userId; via: "cookie" | "loopback" }` |
  `{ kind: "visitor"; accountId; email }` | `{ kind: "anonymous" }`.
  The host already enforces the app's access mode **before** dispatch: on a
  private app only the guardian reaches the handler, on a shared app the
  guardian and the allow-listed visitors, on a public app anyone. A request
  that reaches the handler is already authorized to use the app, so most
  handlers need no caller check at all. Read `caller.kind` only when the app
  differentiates between the guardian and visitors — an owner-privileged
  route (settings writes, agent dispatch, destructive operations) gated with
  `if (request.caller.kind !== "guardian") return Response.json({ error: "forbidden" }, { status: 403 })`,
  or per-visitor data keyed on `caller.email`. Never gate the whole handler
  this way — that rejects every visitor and public caller, so sharing the
  app stops working.
  Never derive identity from headers yourself — the host strips identity
  headers (`X-Rome-User-Id`, `x-rome-visitor-*`) before dispatch, and on a
  public app any surviving header is attacker-controlled. In the web UI,
  `useCaller()` / `getCaller()` from `@rome-os/app-web-sdk` return the same
  identity for UI gating only; enforcement belongs in the API handler.
- `RomeAppContext` — handler-injected context; common fields: `ctx.app.id`,
  `ctx.app.version`, `ctx.log`, `ctx.runAction`, `ctx.db`,
  `ctx.repositories`.
- Returns a standard web `Response`.

**Gotchas:**

- `request.query.limit` is **always `undefined`** — `URLSearchParams` does
  not expose keys as properties. Always `.get("limit")`.
- Casting `request.body` directly to an object type (e.g.
  `request.body as { title?: string }`) compiles but every property is
  `undefined` at runtime — you're casting a `Uint8Array`. Decode and
  `JSON.parse` first.
- `request.body` is `undefined` for empty bodies and GET requests; null-check
  before decoding.

For more complex routing, dispatch further inside the handler or pull in a
lightweight router. The community sample repo has full API-handler examples.

### Creating routines: `system:create_routine`

Call `appContext.runAction("system:create_routine", { ... })` to register a
recurring or one-off scheduled task (or a watched-event routine) with no
confirmation card. The daemon invokes the named action when the trigger
fires. RRULE syntax follows the iCalendar spec. The action returns
`{ status: "error", error }` for caller-fixable problems (bad `localTime`, a
`date`/`rrule` conflict, array `args`) so you can surface the message.

**Recurring routine** — e.g. a daily 03:00 UTC job:

```ts
await appContext.runAction("system:create_routine", {
  name: "daily-dream",
  trigger: {
    type: "schedule",
    tzid: "UTC",               // IANA tz id, NOT "+00:00"
    localTime: "03:00",        // "HH:mm" in tzid's local time
    rrule: "FREQ=DAILY",       // iCal RRULE; recurring
  },
  actionName: "dream:dream",   // canonical action id to execute at trigger time
  args: {},                    // single arg object passed to the action
});
```

**One-off routine** — e.g. a reminder at a specific local time on a
specific date:

```ts
await appContext.runAction("system:create_routine", {
  name: "send-launch-reminder",
  trigger: {
    type: "schedule",
    tzid: "America/Los_Angeles",
    localTime: "09:00",
    date: "2026-06-01",        // "YYYY-MM-DD"; one-off on this calendar date
  },
  actionName: "system:send_message",
  args: { channel: "telegram", threadId: "123", text: "Launch today!" },
});
```

**Input fields** (the trigger matches the `Trigger` types exported by
`@rome-os/app-runtime` — jump-to-definition from your editor is the
authoritative reference):

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | `string` | yes | Human-readable identifier; use for dedup. |
| `trigger.type` | `"schedule" \| "event-bus"` | yes | Schedule or watched-event. |
| `trigger.tzid` | string | schedule | IANA timezone (e.g. `"UTC"`, `"America/Los_Angeles"`). |
| `trigger.localTime` | `"HH:mm"` | schedule | Local wall-clock time in `tzid`. |
| `trigger.rrule` | string | recurring | iCal RRULE, e.g. `FREQ=DAILY`, `FREQ=WEEKLY;BYDAY=MO,WE,FR`. Mutually exclusive with `date`. `FREQ=MONTHLY` must pin `BYMONTHDAY=N`. |
| `trigger.date` | `"YYYY-MM-DD"` | one-off | Mutually exclusive with `rrule`; omit both to fire once at the next `localTime`. |
| `trigger.eventName` | string | event-bus | Watchable event type — find it with `system:search_event_catalog`, which also returns each type's `payloadSchema` (JSON Schema for the fields a `trigger.filter` dot-path can match). |
| `actionName` | string | yes | Canonical `<app-id>:<local-name>` action id to invoke at trigger time. |
| `args` | `Record<string, unknown>` | no | A single arg object (not an array); defaults to `{}`. To fan out, create one routine per arg set. |
| `enabled` | boolean | no | Whether the routine is live on creation (default `true`). |

**Deduplicate before registering** — `listRoutines()` returns everything
already scheduled, and `system:create_routine` is not idempotent on `name`.
Without a guard, every action run will re-register the same routine:

```ts
// `name` is the unique identifier — match on it alone. Don't also match
// on `actionName`, or you will block legitimate sibling routines that
// happen to invoke the same action (e.g. "weekly-dream" alongside
// "daily-dream").
const existing = await appContext.listRoutines();
const alreadyScheduled = existing.some((r) => r.name === "daily-dream");
if (!alreadyScheduled) {
  await appContext.runAction("system:create_routine", { /* ...as above */ });
}
```

### Actions calling actions / agents

App-internal call relationships form a graph: API handlers invoke actions,
actions invoke other actions, actions drive agents, and agents — via the
LLM — call back into actions. At the code level there are only two entry
points:

- **`appContext.runAction(canonicalId, args)`** — makes a nested call and awaits a
  single result. It shares the caller's root and cancellation lifetime, so it
  must be awaited and must never be called with `void`. `canonicalId`
  can be your own action, another app's exposed action (subject to the
  caller agent's action allowlist), or a platform action (`system:summon`,
  `system:create_routine`, `dream:get_action_logs`, `system:fetch_channel_history`, …).
- **`appContext.runAction(canonicalId, args, { detached: true })`** — starts a new
  root execution that is not cancelled with the caller. Awaiting it returns
  an acceptance receipt `{ executionId }`, not an `ActionResult`; use the ID
  to inspect or cancel the independent execution.
- **`agentRunner.run({ agentName, prompt, ... })`** — streams an agent.
  Returns `AsyncIterable<AgentMessage>` and must be consumed event by
  event. While running, the agent will call the actions declared on its
  yaml `actions:` allowlist through LLM tool-use — you **do not** manually
  orchestrate those tool calls.

End-to-end example: an action collects context via a platform action, hands
it to an agent, and the agent in turn calls back into the app's own action.

```ts
// src/actions/research-and-summarize/index.ts
import {
  createAppLogger,
  type Action,
  type ActionConfig,
  type ActionResult,
  type AgentRunnerInterface,
  type AppActionRuntimeDeps,
} from "@rome-os/app-runtime";

const log = createAppLogger("research-and-summarize");

interface Deps {
  agentRunner: AgentRunnerInterface;
}

export function createAction(
  config: ActionConfig,
  deps: AppActionRuntimeDeps<Deps>,
): Action {
  const { agentRunner, appContext } = deps;

  return {
    config,
    inputSchema: {
      type: "object",
      properties: {
        topic: { type: "string" },
        windowHours: { type: "number" },
      },
      required: ["topic"],
    },

    async execute(args): Promise<ActionResult> {
      const topic = args.topic as string;
      const windowHours = (args.windowHours as number) ?? 24;

      // (1) Action calling action — await directly, get an ActionResult.
      const history = await appContext.runAction("system:fetch_channel_history", {
        channel: "discord",
        windowHours,
      });
      if (history.status !== "ok") {
        const reason = history.status === "error" ? history.error : `returned ${history.status}`;
        return { status: "error", error: `fetch_channel_history failed: ${reason}` };
      }

      // (2) Action driving an agent — stream-consume the messages.
      //     researcher.yaml declares `actions: [research-app:notes_create]`,
      //     so the agent picks them up itself during LLM reasoning. You do
      //     not stitch those calls together manually.
      let finalText = "";
      let structured: { summary: string; tags: string[] } | undefined;

      for await (const msg of agentRunner.run({
        agentName: "research-app:researcher",
        prompt: [
          `Topic: ${topic}`,
          `Recent context (last ${windowHours}h):`,
          JSON.stringify(history.data, null, 2),
          "",
          "Research the topic, then return { summary, tags } as structured output.",
        ].join("\n"),
        sharedContext: { topic },        // extra context surfaced to the agent
      })) {
        switch (msg.type) {
          case "text":
            // Streaming text — forward to the frontend for a streaming UI.
            break;
          case "result":
            finalText = msg.content as string;
            structured = msg.structuredOutput as
              | { summary: string; tags: string[] }
              | undefined;
            break;
          case "error":
            log.error("researcher failed", { error: msg.error });
            return { status: "error", error: msg.error };
        }
      }

      // (3) Once we have the agent's output, write it to storage —
      //     another action-to-action call.
      if (structured) {
        await appContext.runAction("research-app:notes_create", {
          title: `Research: ${topic}`,
          content: structured.summary,
          tags: structured.tags,
        });
      }

      return { status: "ok", data: { topic, summary: structured?.summary ?? finalText } };
    },
  };
}
```

The matching `researcher.yaml` (the declaration side that lets the agent call
back into actions):

```yaml
name: researcher
description: Researches a given topic and produces a structured summary
tier: medium
reasoningEffort: high
# `acceptEdits`, not `bypassPermissions` — pairing bypass with
# world-touching tools like WebFetch is flagged as an anti-pattern in
# SKILL.md. Reserve `bypassPermissions` for fully-trusted,
# read-only, or sandboxed agents.
permissionMode: acceptEdits
tools: [Read, WebSearch, WebFetch]
actions:                       # ← agent → action access is exposed here
  - research-app:notes_create
outputSchema:
  type: object
  required: [summary, tags]
  additionalProperties: false
  properties:
    summary: { type: string }
    tags: { type: array, items: { type: string } }
systemPromptPrefix: |
  You are the researcher agent. Read the input topic and context, run
  the WebSearch tool when needed, and return { summary, tags } as the final
  structured result.
```

Takeaways:

- **Action → action:** `appContext.runAction(canonicalId, args)` returns
  `Promise<ActionResult>`. Always await it, then narrow on `result.status`
  before reading `data` / `error`. Never use `void runAction(...)` for this
  nested form. With `{ detached: true }`, it instead creates a new root and
  returns `Promise<{ executionId: string }>` once main accepts the dispatch.
- **Agent → action:** routed through the agent yaml's `actions:` allowlist
  plus LLM tool-use. **Do not** hand-orchestrate the agent's tool-call
  order in code.
- **Action → agent:** `agentRunner.run(...)` returns an `AsyncIterable` and
  must be consumed to completion. Returning early cancels the agent
  session.
- **Reusing existing agents:** to invoke another app's agent, always go
  through `system:summon`
  (`appContext.runAction("system:summon", { agentName: "assistant:assistant", prompt, sessionId? })`).
  Do not call `agentRunner.run` directly on agents that aren't yours.

## Frontend SDK: `@rome-os/app-web-sdk`

The web entry `src/web/App.tsx` **must default-export** a React component
accepting `{ bootstrap }`. The SDK handles mounting, style injection, and
shadow DOM wrapping.

```tsx
import {
  fetchAppApi,
  getCurrentAppPath,
  navigateToApp,
  navigateRome,
  subscribeToAppPath,
  buildAppUrl,
  startChat,
  type RomeAppBootstrap,
} from "@rome-os/app-web-sdk";
import "./styles.css";

export default function App({ bootstrap }: { bootstrap: RomeAppBootstrap }) {
  // bootstrap.appId / bootstrap.version / bootstrap.routeBase / bootstrap.shell
  return <main>...</main>;
}
```

### Common helpers

| API | Purpose |
|---|---|
| `fetchAppApi(path, init?)` | Calls this app's API; auto-prefixes `/api/apps/<appId>/<path>`, supports query strings in `path` (e.g. `"repos?limit=50"`), normalizes query encoding, and adds auth headers. ⚠️ **Never pass an empty string or `"/"`** — `fetchAppApi("")` resolves to `/api/apps/<appId>` which is the platform deployment-status endpoint, not your app API. Always pass an explicit subroute, e.g. `fetchAppApi("home")` or `fetchAppApi("state")`. |
| `getBootstrap()` | Returns `RomeAppBootstrap` outside of a component context |
| `getCurrentAppPath()` | Current in-app sub-route, e.g. `"settings"` |
| `subscribeToAppPath(cb)` | Subscribes to in-app route changes; returns an unsubscribe function |
| `navigateToApp(path)` | Navigates to an in-app sub-route (pushState) |
| `navigateRome(payload)` | Deep-links into a **host** route (chat, settings, memory, another app). Typed union — see below. |
| `buildAppUrl(path)` | Builds a shareable, fully-qualified URL |
| `startChat(opts)` | Opens a fresh webchat session, posts `opts.message` as the first user turn (this kicks off the agent), and navigates to `/chat/<id>` unless `navigate: false`. Returns `{ sessionId }` (async). |

#### Handing the guardian into a chat

Two complementary surfaces — pick by whether the first message should send on
its own or wait for the guardian.

`startChat({ message, agentName?, projectPath?, navigate? })` creates a session
and **sends** `message` immediately (kicking off the agent), then navigates to
the chat. Use it to fire-and-go. Set `agentName` to target a specific agent —
**pass your app's own agent name** to start the chat with it (omit → the default
host agent). `projectPath` anchors the session to a project; `navigate: false`
creates the session without leaving the app (you get `sessionId` back to route
yourself). It throws if the session can't be created, so wrap the call.

`navigateRome(payload)` deep-links into a host route — a typed discriminated
union, so a bad param is a compile error, not a 404. It's a soft navigation (no
reload, no state loss). The variants:

| Payload | Destination |
|---|---|
| `{ path: "chat", sessionId }` | An existing chat session. |
| `{ path: "chat/new", draft?, skill? }` | A fresh composer, **un-sent**. `draft` pre-fills the message so the guardian edits and commits it themselves; `skill` pre-pins a structured skill chip — any catalog skill name, sent as a field, never parsed from the text. |
| `{ path: "settings", tab? }` | Settings, optionally a specific tab. |
| `{ path: "memory", file? }` | Memory, optionally a specific file. |
| `{ path: "apps", appId, subPath? }` | Another app's page. |

So for a friendly onboarding hand-off, prefer `navigateRome({ path: "chat/new",
draft, skill })`: the guardian lands on a pre-filled composer and reviews before
sending — and it's the only way to pre-pin a skill chip. Reach for `startChat`
when the app should commit the first message itself.

See the community sample repo for full web app examples.

### Styling

- Tailwind v4 and the `@rome-os/ui` component kit are pre-installed.
  `styles.css` is one import — `@rome-os/app-web-sdk/styles`, which carries
  Tailwind, `tw-animate-css`, the SDK's own `@source`, and the kit canon (the
  token vocabulary, the `@custom-variant` set, the base resets, and the kit's
  `@source` list). Keep it thin and add only app-specific rules below it.
- **Keep `@rome-os/ui` in the app's `package.json`.** The SDK takes the kit as
  an optional peer dependency, so the app supplies it and the tree holds one
  copy. Two copies would let a component read a token its own stylesheet no
  longer emits, and the build would still pass. Drop the dependency and the
  build fails to resolve `@rome-os/ui/styles.css`, which is the loud version of
  the same problem.
- A kit component that ships its own stylesheet (`@rome-os/ui/markdown.css`)
  needs that import here too — the host document's copy does not cross the
  shadow boundary — plus its optional peers installed. The kit's README says
  which components those are.
- Author custom CSS variables in a `:root` block. The host rewrites `:root` to
  `:host` when it injects the bundle into the shadow root
  (`packages/web/src/components/rome-app-host.tsx`), which is what makes an
  app-declared value beat the inherited host token.
- **Read only the tokens your own bundle supplies.** The host promises one
  thing across the shadow boundary: the theme layer, meaning color and shadow
  values, which arrive as inherited custom properties and track the live theme
  and mode. Everything else — geometry, typography, the control scale — holds
  the same value under every theme, and the two imports above are what put it
  in your bundle. Custom properties inherit and inheritance cannot be narrowed,
  so your app also reaches every other property the host page happens to
  declare. Reading one renders correctly in the Rome dashboard and breaks
  against any other host, and no build or test in your app catches it. An app
  that ships no kit stylesheet declares the few constants it uses itself.
- Components come from the kit — `import { Button } from "@rome-os/ui/button"`,
  one subpath per component. Do not copy a component the kit publishes into
  `components/ui/`; the copy is frozen and drifts. See
  [`AUTHORING.md` → Respect the component library](./AUTHORING.md#2-respect-the-component-library).
- Only for a primitive the kit does not publish (e.g. `pagination`), run
  `pnpm dlx shadcn@latest add <component>` from the app root to drop a
  canonical recipe into `components/ui/`, then re-wire its geometry to the host
  control scale (`--control-*` / `--field-*`) and its `Portal` to
  `getPortalContainer()`.
- Icons: `lucide-react` is already a runtime dependency (and the kit's peer).

### Shadow DOM & Input Behaviour

Rome apps mount inside a **Shadow DOM**. This affects browser input APIs in
non-obvious ways. Be aware of the following before writing any pointer,
drag, or full-screen code.

#### Pointer Lock

`document.pointerLockElement` always targets the **shadow host** (the custom
element Rome inserts into the page), not a canvas or element inside your
shadow root. A strict equality check like `document.pointerLockElement === canvas`
therefore always evaluates to `false`, even when the lock is active.

**Correct check pattern:**

```ts
function isPointerLocked(canvas: HTMLElement): boolean {
  const el = document.pointerLockElement;
  return (
    el === canvas ||
    (el !== null && el.contains(canvas)) ||
    shadowRoot?.pointerLockElement === canvas
  );
}
```

Where `shadowRoot` is the `ShadowRoot` that hosts your app — accessible via
`canvas.getRootNode()` cast to `ShadowRoot`.

**Drag-to-look fallback** — pointer lock is denied in some browser/sandbox
configurations. Always add a mouse-drag fallback so the experience degrades
gracefully:

```ts
canvas.addEventListener("pointerlockerror", enableDragFallback);
requestPointerLock().catch(() => enableDragFallback());
// also set a timeout: if lock hasn't engaged 450 ms after a gesture, fall back
```

In the fallback, treat `mousemove` (with button held) as a rotation delta.

#### Trusted Input Events for Testing

Standard `new MouseEvent(...)` dispatches are **untrusted** and may be ignored
by canvas-based engines that check `event.isTrusted`. When writing headless or
integration tests, use the CDP command `Input.dispatchMouseEvent` over a raw
WebSocket connection — those events arrive as trusted.

```ts
// Node 24 — raw CDP over WebSocket (useful for verifying 3D/canvas apps headlessly)
ws.send(JSON.stringify({
  id: 1,
  method: "Input.dispatchMouseEvent",
  params: { type: "mousePressed", x: 400, y: 300, button: "left", clickCount: 1 },
}));
```

#### Other Shadow DOM Notes

- Global selectors (`body`, `html`, `*`) in `styles.css` do not apply inside
  the shadow root — scope everything to `:host` or a descendant selector.
- `document.activeElement` points to the shadow host, not the focused element
  inside the shadow — use `shadowRoot.activeElement` instead.
- Floating UI / portals must use `getPortalContainer()` from the SDK so they
  render inside the shadow root rather than escaping to `document.body`.

### Rome App access

- Rome core and the rome apps are served in the same process on port 4141.
- Rome app web UI runs on: `http://localhost:4141/apps/<appId>`
- Rome app api runs on: `http://localhost:4141/api/apps/<appId>/...`
- User can only access the rome app via: `https://<rome-domain>/apps/<appId>`, so when you present the link to the user,
use [<appName>](/apps/<appId>) to get the correct URL. DO NOT present the localhost URL or any domain URL to the user.
- The app is mounted at `/apps/<appId>/*`, so any sub-path deep-links straight to
  a specific view: `/apps/<appId>/<detailId>` (e.g. `/apps/tickets/T-1423`,
  `/apps/calendar/week/2024-06`). Build detail/item views as their own routes and
  hand the user the deep link — `[<label>](/apps/<appId>/<detailId>)` — so they
  land directly on the entity instead of opening the app root and searching.
- In the web bundle, read the current sub-route with `getCurrentAppPath()` /
  `subscribeToAppPath(cb)` and navigate with `navigateToApp("<detailId>")`
  (soft pushState). From another app, deep-link with
  `navigateRome({ path: "apps", appId, subPath: "<detailId>" })`. See
  "Frontend SDK → Common helpers" above. AUTHORING.md §9 covers the design rule.

### Mobile / responsive design

Rome apps render inside the dashboard shell on both desktop and mobile
(the dashboard is used on phones routinely). The frontend **must** work
at narrow viewports — design mobile-first, then progressively enhance
for larger screens.

**Layout**

- Use Tailwind's responsive prefixes (`sm:` 640px, `md:` 768px, `lg:`
  1024px). Default styles target mobile; add `md:` / `lg:` overrides
  for wider viewports — not the other way around.
- Prefer single-column flows on narrow screens; switch to multi-column
  grids only at `md:` or `lg:`. Example:

  ```tsx
  <div className="grid grid-cols-1 gap-4 md:grid-cols-2 lg:grid-cols-3">
    {items.map((it) => <Card key={it.id}>...</Card>)}
  </div>
  ```

- Avoid fixed widths (`w-[480px]`) on top-level containers. Use
  `w-full max-w-screen-md mx-auto` patterns so the layout adapts.
- Tables overflow easily — wrap them in
  `<div className="overflow-x-auto">…</div>` or fall back to a stacked
  card list at narrow breakpoints.
- Never rely on hover-only affordances. Every action reachable by
  hover must also be reachable by tap (visible button, long-press
  menu, etc.).

**Touch targets & spacing**

- Interactive elements need a hit area of at least **44×44 px**. Kit control
  defaults are close but verify on dense lists.
- Increase tap padding rather than shrinking font size when space is
  tight — `px-3 py-2` minimum on small buttons.
- Keep at least `gap-2` (8 px) between adjacent tappable elements so
  users don't mis-tap.

**Typography**

- Body text: `text-base` (16 px) — anything smaller is hard to read
  and triggers iOS Safari's auto-zoom on `<input>` focus. If you
  must shrink, do so only at `md:` and up.
- Headings should also scale: `text-xl md:text-2xl lg:text-3xl`.
- Use `leading-relaxed` for paragraph copy on mobile; default leading
  feels cramped at 16 px.

**Forms & input**

- Inputs: width `w-full` on mobile, constrain inside a `max-w-md`
  container instead of fixing the input width.
- Set `inputMode` and `autoComplete` correctly so mobile keyboards
  pick the right layout (`inputMode="numeric"`, `type="email"`,
  `autoComplete="one-time-code"`, …).
- Group buttons vertically on narrow screens:
  `flex flex-col gap-2 sm:flex-row sm:gap-3`.

**Safe area & viewport**

- The shell already injects the right `<meta name="viewport">`. Do
  not override it.
- For full-bleed UIs, respect the iOS notch with the Tailwind
  `pb-[env(safe-area-inset-bottom)]` pattern on bottom-fixed bars.

**Validation**

Before declaring a UI change done, test at **375 px wide** (iPhone SE
class) in Chrome DevTools' device emulator and verify that:

- All primary actions are reachable without horizontal scroll.
- No text is cut off, no buttons are flush against viewport edges.
- Form fields can be focused and typed into without zoom jumps.
- Long content scrolls naturally (no nested scroll traps).

## Database & Migrations

### Storage model: shared SQLite + table prefix

App data is **not** written to a separate SQLite file. Every app table lives
in the same system SQLite (`~/.rome/<profile>/rome.db`), isolated via a
**`tablePrefix`**.

- Enable the DB in `app.yaml`:

  ```yaml
  db:
    migrations: db/migrations
    tablePrefix: myapp           # Typically equals the appId
  ```

- Real table names are `<tablePrefix>__<logical_name>` (double underscore),
  joined automatically by the daemon. Your Drizzle schema only uses the
  logical names.
- The migration history table is
  `__drizzle_migrations_app_<tablePrefix>`, isolated from other apps' and
  the system's migration records.
- Non-DB file data (caches, uploads, …) lives at
  `~/.rome/<profile>/apps/data/<appId>/`. That is a separate path and has
  nothing to do with the table-prefix mechanism.
- `system:app_management { op: "uninstall", purge: true }` drops the
  `<tablePrefix>__*` tables and the migration table, and removes
  `apps/data/<appId>/`.

### Workflow

1. Define tables in `src/db/schema.ts` using Drizzle (use logical names —
   no prefix).
2. From the app directory run **`pnpm db:generate`** — the script is
   pre-baked into the template `package.json` and is equivalent to:

   ```sh
   drizzle-kit generate
   ```

   It reads the `drizzle.config.ts` at the app root:

   ```ts
   // drizzle.config.ts
   import { defineConfig } from "drizzle-kit";
   export default defineConfig({
     schema: "./src/db/schema.ts",
     out: "./src/db/migrations",
     dialect: "sqlite",
     migrations: { table: "__drizzle_migrations_app_myapp" },
     tablesFilter: ["myapp__*"],   // Scope drizzle-kit to your tables only
   });
   ```

   Output goes to `src/db/migrations/` (SQL files plus a `meta/` snapshot).
   Every time you change `schema.ts` you **must** rerun
   `pnpm db:generate` to produce a new migration file. **Never hand-edit
   existing migration SQL** — only append new files.

3. Centralize data access behind repositories in `src/db/repositories/`,
   pulling the connection from `appContext.db`. **Do not** inline raw SQL
   in actions or API handlers:

   ```ts
   // src/db/repositories/notes.ts
   import { eq } from "drizzle-orm";
   import { notes } from "../schema.js";
   export function createNotesRepository(db: AppDb) {
     return {
       list: () => db.select().from(notes).all(),
       byId: (id: string) => db.select().from(notes).where(eq(notes.id, id)).get(),
       insert: (row: typeof notes.$inferInsert) => db.insert(notes).values(row).run(),
     };
   }
   ```

4. `install` automatically runs any pending migrations for the app — no
   manual migrate step.
5. If the app does not need persistence, delete the whole layer (`src/db/`,
   `drizzle.config.ts`, the `db:` block in `app.yaml`, the `drizzle-*`
   dependencies and the `db:generate` script from `package.json`).

The template's `src/db/README.md` has more detail.

## Hooks

A hook is a callback registered against the daemon's event loop. The
canonical example is the `channel-message` hook: every incoming channel
message flows through it, and the hook decides whether to dispatch the
sentinel agent.

Hook directory layout:

```
src/hooks/<name>/
├── hook.yaml      # Declares the hook type and trigger conditions
└── index.ts       # Implementation: export function createHook(deps): Hook
```

The exact shape varies by hook type. See the community sample repo for an
inbox-style channel hook.

## Boundaries & Anti-patterns

- App code **must not** `import` source from `packages/core` (or any other
  monorepo-internal package). The published boundary is `@rome-os/app-runtime`
  (backend), `@rome-os/app-web-sdk` (web SDK + CLI), and `@rome-os/ui` (the
  component kit, `src/web/` only) — nothing else.
- Do not cross-`import` between apps. If two apps share logic, move it to
  the SDK or extract a new app.
- Do not put global selectors (`body`, `html`) into `styles.css` — they do
  not apply inside the shadow DOM.
- Do not hand-edit `dist/` or `app.lockfile`.
- When an action has side effects, declare `sideEffects: write` honestly.
  Approval policies decide whether to intercept based on this field.
