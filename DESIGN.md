## Brand
- Personality: Quiet, capable, operator-first, and personal without becoming decorative.
- Trust signals: Plain language, predictable controls, explicit access states, restrained surfaces, and visible error states for auth failures.
- Avoid: Marketing-style hero composition inside the app, decorative gradients/orbs, saturated color as ornament, vague security copy, and hidden access side effects.

## Product goals
- Goals: Let guardians find and resume any chat quickly by title or project through a visible action and a standard command shortcut; render inline and display mathematics consistently anywhere Rome's shared Markdown renderer is used; let guardians decide who can use an installed app; make public, private, and Rome Cloud email-restricted access visibly distinct; give apps a typed visitor identity for custom in-app authorization; make file and folder actions discoverable and operable with touch, mouse, pen, keyboard, and assistive technology; let operators compare daily model-token and estimated-dollar usage by Rome Cloud guardian account; let Rome admins safely move an existing account to a new verified Google email without changing its stable account identity or connected data.
- Non-goals: General organization/team RBAC, per-route policy editing in the dashboard, anonymous identity collection outside access-gated app visits, account merging, per-user session revocation, changing provider resource connections, or synchronizing third-party billing/contact records as part of an email change.
- Success signals: The Chats header exposes search beside list settings; `Command/Ctrl+K` opens the same search from anywhere in the guardian shell; a guardian can find active or archived chats by chat title or project identity and open a result without leaving the keyboard; inline and display `$$...$$` expressions render through KaTeX with MathML while single-dollar currency remains plain text; guardians can set access without leaving the app card; unauthorized visitors see a clear sign-in path; app authors can read `viewer.email` and `viewer.accountId`; protected app APIs and bundles are not reachable by visitors outside the allowed email list; every file-browser surface exposes the same applicable actions without requiring discovery of a hidden gesture; an admin can change a user's canonical email from the Users table, sees exactly what remains and what is unlinked, and receives a concrete Google sign-in handoff after success.

## Personas and jobs
- Primary personas: The guardian managing a Rome instance and its files; invited Rome Cloud users opening a shared app; app builders adding custom access behavior; operators monitoring usage across Rome Cloud guardian accounts; trusted Rome admins handling account-access changes.
- User jobs: Find and resume an earlier chat without scanning groups or changing archive filters; browse and act on project or memory files from any device; share one app without exposing the full dashboard; restrict an app to known Rome Cloud email addresses; let app code branch on visitor identity; rank guardian accounts by tokens and estimated spend and inspect their daily trend; preserve a user's existing account, instance, and data while replacing the Google identity used for future sign-in.
- Key contexts of use: Guardian-only administration, keyboard-heavy desktop navigation, compact phone/tablet chat and file browsing, wide two-pane file browsing, hybrid touch-and-pointer devices, hosted public edge visits, embedded app routes, full-screen app routes, app API handlers, and low-frequency high-trust account support operations.

## Information architecture
- Primary navigation: Existing app dashboard navigation remains unchanged; the Chats section header keeps search and list settings simultaneously visible; access management lives on each app card's action menu.
- Core routes/screens: Guardian shell chat sidebar, chat search command dialog, apps index, access dialog, settings public access section, embedded app shell, full app shell, visitor auth callback, Rome Cloud Admin → Users and its account-email dialog, ClickStack guardian-usage dashboard.
- Content hierarchy: Chat search query first, matching chats second, project/status context within each result, and keyboard guidance last; access mode first, email list only when Rome Cloud email mode is selected, sign-in gate only when an app requires visitor identity and the current visitor is missing or not allowed; account email dialog identifies the target user and current email first, new verified Google email second, effects and unaffected data third, and the confirmation action last.

## Design principles
- Principle 1: Access state is a property of the app, not a global mystery setting. Show and edit it where the guardian is already managing the app.
- Principle 2: The public shell may be reachable, but protected app content and APIs should only load after the visitor is allowed.
- Principle 3: File actions have a visible primary affordance where layout density permits. Long-press, right-click, and drag are accelerators; compact grid users can switch to list view for explicit per-item action buttons.
- Principle 4: Usage views keep tokens and currency in separate visualizations, use the Rome Cloud account slug already present as `service.instance.id`, and retain `unknown` as a visible data-quality category.
- Principle 5: A shortcut is an accelerator, never the only discovery path. The persistent search icon and `Command/Ctrl+K` invoke one shared chat-search experience.
- Principle 6: Account support actions preserve stable identity. Changing email updates the existing account and invalidates only its Google sign-in linkage; the interface names both effects before confirmation.
- Principle 7: Markdown capabilities belong to the shared renderer. Math uses Streamdown's default double-dollar syntax for both inline and display expressions, avoiding ambiguity with currency.
- Tradeoffs: Chat search matches session metadata (title and project name/path), not message bodies, keeping the action immediate and within the existing session-list API; it includes archived chats and labels them rather than inheriting the sidebar's current status filter. A simple email allow-list is easier to audit than a broad policy builder; app-level custom logic stays possible through `viewer`, but the platform still provides a secure default gate. Compact list rows spend space on an explicit action button, while grid cards stay visually clean and rely on long-press/right-click plus the visible list-view alternative. Email change lives in a row overflow menu to keep the dense user table calm; a focused confirmation dialog carries the security explanation and post-change handoff. Existing sessions remain active because per-user revocation does not exist, so the UI states that limitation instead of implying revocation.

## Visual language
- Color: Mostly neutral surfaces with semantic color reserved for status, danger, and errors.
- Typography: Geist-style sans hierarchy already used in the web app; compact titles for dialogs and panels.
- Spacing/layout rhythm: Dense but readable operational UI; dialogs use clear groups and short helper text.
- Shape/radius/elevation: Reuse existing UI primitives and 8-14px radii already present in `packages/web/src/components/ui`.
- Motion: Minimal transition-only feedback; no decorative motion for auth or access changes.
- Imagery/iconography: Use lucide icons for action affordances; access uses globe/mail/user-style symbols rather than custom illustration.

## Accessibility
- Target standard: WCAG 2.2 AA for new UI; aim for 44-48px touch targets on compact surfaces.
- Keyboard/focus behavior: `Command+K` on Apple platforms and `Ctrl+K` elsewhere open chat search; focus moves to the query, Up/Down changes the active result, Enter opens it, and Escape closes with focus restored. Access mode choices, changed-file rows, file action buttons, account row menus, and action-sheet items must be keyboard reachable and visibly focused; dialogs and menus preserve Radix focus trapping/restoration and Escape behavior. The account-email dialog initially focuses the email field, Enter submits a valid idle form, and the dialog cannot close while the mutation is in flight.
- Contrast/readability: Helper text and errors must pass contrast on surface backgrounds; destructive/error text uses existing semantic tokens.
- Screen-reader semantics: Chat search follows the combobox/listbox pattern, announces result state, and exposes active, archived, and current-chat context without relying on color. Rendered mathematics retains KaTeX's MathML representation for assistive technology. Dialogs require accessible titles/descriptions; file action icon buttons and account row action buttons need item-specific labels; access choices need clear names and descriptions; email validation and mutation errors are associated with the field and announced without relying on color.
- Reduced motion and sensory considerations: No motion or long-press dependency; loading states use text and disabled controls; sheet motion respects `prefers-reduced-motion`.

## Responsive behavior
- Supported breakpoints/devices: Compact file-browser surfaces below the 1024px container breakpoint, wide two-pane file browsers, desktop guardian dashboard, phones/tablets, and hybrid touch-plus-pointer devices.
- Layout adaptations: Chat search stays viewport-inset on small screens, limits its result region to available height, and keeps result rows touch-sized; compact file rows expose a persistent actions button and use a bottom action sheet; compact grid cards omit per-card ellipses and use long-press/right-click, with list view as the explicit-action alternative; wide tree rows reveal actions on hover/focus and keep them visible on touch; app and account row menus remain compact; access and account-email dialogs stack content within the modal width.
- Touch/hover differences: Controls must not depend on hover-only disclosure across the complete file-browser surface. Long-press opens the same actions as visible list/tree buttons, and the grid/list switch provides an explicit alternative for grid users. Native drag is enabled from the active mouse pointer, not inferred from a viewport media query.

## Interaction States
- Loading: Save buttons and sign-in buttons disable and show in-progress labels.
- Empty: Email-list mode requires at least one valid email before save.
- Error: Invalid emails are reported inline with the rejected entries; visitor auth start failures stay on the gate panel.
- Success: Access dialog closes and the app list refreshes.
- Disabled: Save is disabled while mutation is in flight; unrelated destructive app actions stay separate.
- Chat search: Opening starts with the most recent chats, typing filters across chat title and project name/path, archived matches carry an explicit label, clearing restores recents, and selecting a result closes the dialog before navigation. A failed request offers retry without discarding the query.
- File actions: Opening a menu prepares the same action-path selection regardless of ellipsis, long-press, right-click, or keyboard invocation, but must never change folder navigation or the dashboard behind the menu; releasing a long-press must not also open/select/toggle the item.
- Offline/slow network, if applicable: Visitor login start shows a network-specific failure; app manifest load failures use existing app error panels.
- Usage data gaps: Missing accounting contributes zero; a missing instance id is grouped under `unknown` instead of being dropped.
- Account email: The dialog rejects malformed, unchanged, and already-used addresses inline; submission atomically updates the canonical lowercase email and removes only the Google federated identity; success keeps the dialog open long enough to explain that the user must sign in with the matching verified Google account, while stable account data, provider connections, and current sessions remain unchanged.

## Content Voice
- Voice: [`docs/ui/VOICE.md`](docs/ui/VOICE.md) governs how every string a guardian reads sounds. The lines below are surface-specific terminology.
- Tone: Clear, calm, and explicit about who gets access.
- Terminology: Use "Search chats", "Recent chats", "Active", "Archived", and "Current" for chat search; use "Private", "Public", and "Rome Cloud email list" for app access; use "visitor" in code but avoid making end users parse that term.
- Microcopy rules: Describe chat search as matching titles or projects and avoid implying message-body search; name the effect of an option, not the implementation; keep access warnings short; show exact invalid email addresses when validation fails. Use “Change account email” for the admin action, “Google sign-in” for the identity effect, and avoid implementation terms such as “federated identity,” “subject,” or “rebind” in UI copy.
- Usage terminology: Say "Guardian account" for the Rome Cloud account slug, "Estimated cost" for provider-derived USD values, and label fixed day buckets as UTC.

## Implementation Constraints
- Framework/styling system: React, Radix primitives, lucide-react icons, Streamdown with shared code, Mermaid, and KaTeX math plugins, existing Tailwind-style utility classes, i18next locale files.
- Design-token constraints: Reuse existing semantic tokens (`surface`, `border`, `muted-foreground`, destructive tokens) instead of adding a new palette.
- Performance constraints: Chat metadata is fetched lazily when search opens, recent results are capped before rendering, and filtering remains local for immediate keystroke response; app manifest and access checks must remain small and cache-safe; visitor auth state should not require loading app bundles before authorization; usage queries must be time-bounded, restricted to `model.turn`, and return limited result sets.
- Compatibility constraints: The project is in development, so no backward compatibility migration UI is required; normalization should still tolerate older public-access payloads.
- Test/screenshot expectations: Shared Markdown tests cover inline and display math, MathML output, and preservation of single-dollar currency text. Chat search covers trigger discovery, platform shortcut selection, lazy all-status fetch, title/project filtering, archived/current context, keyboard selection/navigation, empty/error/retry states, focus behavior, and compact/wide screenshots. Cover access config normalization, auth probe behavior, Caddy route generation, app list UI mutations, and app shell gate behavior when changed. Account-email changes cover admin authorization, strict JSON validation, normalization, missing/conflicting/unchanged users, atomic canonical-email plus Google-link mutation, preservation of provider connections, dialog validation, saving lock, success handoff, and row refresh. File-action changes cover long-press timing/cancellation, click suppression, row-versus-root menu boundaries, active-pointer drag behavior, and list/grid compact affordances; physically verify iOS Safari and Android Chrome for gesture changes. Usage dashboards require dry-run schema review, live apply, and query validation for each tile.

## Open questions
- [ ] Should visitors have an explicit "switch Rome Cloud account" control after a forbidden email, or is clearing the visitor cookie enough for now? Owner: product. Impact: visitor recovery UX.
- [ ] Should the gateway distinguish fully public apps from Rome Cloud email-restricted apps visually? Owner: product/design. Impact: expectations before sign-in.
- [ ] Should app authors be able to request more visitor profile fields beyond account ID and email? Owner: platform. Impact: privacy and API surface.
- [ ] Should the file browser add an explicit destination picker for a non-drag “Move to…” action? Owner: product/design. Impact: WCAG 2.5.7 parity and mobile file organization.
- [ ] Should account support add per-user session revocation alongside email changes? Owner: product/security. Impact: compromised-account recovery; current sessions otherwise remain valid until expiry.
